### 16.1 设计目标与影响面

**目标**：在「公司估值」的「基期现金流」选取方式中新增第 5 项「自定义」——基期自由现金流由用户手动录入（可选 千/万/亿/元 单位，换算为元），覆盖 FR-1~FR-10；其余 DCF 公式、折现率/增长率口径、金融资产/长投/债务口径与前置条件**全部不变**（需求第 5 节）。

| FR | 落点 |
| --- | --- |
| FR-1 新增第 5 项「自定义」，选中后展开输入+单位 | 前端 `valFCFModes` + 模板（16.7）；后端 `valFCFCustom`（16.5） |
| FR-2 单位 千/万/亿/元（元=不选单位）、默认「亿」 | 参数 `fcf_custom_unit` 枚举（16.2）；前端单位下拉（16.7） |
| FR-3 最多 2 位小数、换算不四舍五入、换算后 ≤1e14 元 | 后端 `ParseCustomFCF`（16.5.1）；前端 `validateCustomFCF`（16.7.2） |
| FR-4 空/非数字/≤0/超限提示，不发起计算；后端兜底 | 前端校验（16.7.2/16.7.4）；后端 `ParseCustomFCF` + `fcf<=0` 兜底（16.5.3） |
| FR-5 研发调整仍叠加（自定义值 + 扩张额） | `ComputeValuation` 研发块位置不变（16.5.3） |
| FR-6 自定义时「选取年数」隐藏且不携带 | 前端 `v-if` + 请求白名单（16.7.3/16.7.4）；后端忽略 `fcf_years` |

| FR-10 仅点「计算估值」触发 | 沿用现状（16.7.4） |

### 16.2 参数契约与单位枚举

**请求参数**（`GET /api/stock/:code/valuation`，在既有参数基础上新增 2 个，仅在 `fcf_mode=custom` 时生效）：

| 参数 | 类型 | 必填 | 缺省 | 说明 |
| --- | --- | --- | --- | --- |
| `fcf_mode` | string | 否 | `latest` | 新增取值 `custom`（自定义） |
| `fcf_custom_value` | **string** | `custom` 时必填 | — | 用户录入的数值原文，如 `6.5`；**以字符串传递**（保留小数原文，便于后端按原文校验位数与精度，`custom` 时为空即报错） |
| `fcf_custom_unit` | string | 否 | `yi` | 单位枚举：`yuan`/`qian`/`wan`/`yi`（`custom` 时缺省按 `yi`） |
| `fcf_years` | int | 否 | 0 | `custom` 时**忽略**（前端也不携带） |

**数值为何用 string 而非 float64**：`fcf_custom_value` 走 URL query，本来就是字符串；在 Go 侧保持 `string` 到校验完成，可直接对「原文」做「≤2 位小数」的格式判定（`ParseFloat` 之后再判位数不可靠，如 `1.230`/`1e5` 已丢失原貌），并在同一处用精确十进制运算换算，避免「先转 float 再兜底校验」引入的舍入。**换算完成后**才落到 `model.ValuationParams.FCFCustomValue float64`（元），供后续 DCF 使用。

**单位枚举**（→ 元的换算系数，全部为精确整数）：

| `fcf_custom_unit` | 界面文案 | 系数（→ 元） |
| --- | --- | --- |
| `yi` | 亿（**默认**，Q2） | 1e8 |
| `wan` | 万 | 1e4 |
| `qian` | 千 | 1e3 |
| `yuan` | 元（=「不选单位」，Q6） | 1 |

> 采用 ASCII key 而非中文字面值，与既有 `fcf_mode`/`model` 的 ASCII key 风格一致，避免 URL 编码与前后端字面比对歧义；界面用中文 label。「元」作为显式枚举项承载「不选单位」，杜绝「看起来没选、实际按某单位算」的歧义（Q6）。

**校验规则表**（后端 `ParseCustomFCF`，顺序即判定顺序）：

| # | 条件 | 结果 |
| --- | --- | --- |
| 1 | `fcf_custom_unit` 不在枚举内 | 错误「未知的基期现金流单位」（`unit` 缺省时按 `yi`，不会触发） |
| 2 | `fcf_custom_value` trim 后为空 | 错误「请输入基期现金流」 |
| 3 | 不匹配 `^[0-9]+(\.[0-9]{1,2})?$`（含负号、字母、`1e5`、`.5`、`5.`、`1.234`） | 错误「基期现金流格式不正确（最多 2 位小数）」 |
| 4 | 换算值 ≤ 0（即原文为 `0`/`0.00`） | 错误「基期现金流需大于 0」 |
| 5 | 换算后金额 > 1e14 元（Q4） | 错误「基期现金流换算后金额过大（上限 100 万亿元）」 |
| 6 | 上表全通过 | 返回换算后的元值（`float64`） |

**错误码**：全部沿用 `{code:1, message, data:null}`，HTTP 200（与既有 `parseValuationParams` 的折现率校验一致）；成功仍为 `{code:0, data:ValuationResult, message:"ok"}`。

### 16.3 数据模型（`internal/model/valuation.go`）

```go
type ValuationParams struct {
    // ...既有字段不变...
    FCFMode        string  // 基期自由现金流选取方式：latest / average / median / trim_mean / custom（缺省 latest）
    FCFYears       int     // 选取年数（average/median/trim_mean 用，缺省 3；custom 忽略）
    AdjustRD       bool    // 是否调整研发费用
    FCFCustomValue float64 // 自定义基期自由现金流（元，已按 fcf_custom_unit 换算；仅 FCFMode=custom 用）
}

type ValuationResult struct {
    // ...既有字段不变...
    FCFMode      string
    FCFModeName  string // custom 时为「自定义」
    FCFYears     int    // custom 时为 0（omitempty 不输出）
    FCFCustomValue float64 `json:"fcf_custom_value,omitempty"` // 自定义换算后的元值（仅 custom，回显）
    FCFCustomUnit  string  `json:"fcf_custom_unit,omitempty"`  // 单位 key（仅 custom，回显）
    // ...其余不变...
}
```

- `FCFCustomValue`/`FCFCustomUnit` 均 `omitempty`：非自定义模式下为零值，**不出现在响应里**，既有调用方逐字段兼容。
- 口径：`BaseFCF`（既有字段）在自定义模式下 = `FCFCustomValue + RDAdjustment`（即已含研发叠加，见 16.5.3），前端结果区仍读 `base_fcf`，无需改字段。
- 单位换算口径「千/万/亿 = ×1e3/1e4/1e8、元 = ×1」以本文件与 `docs/R4-公司股票估值/公司股票估值.md` 双处登记（延续「口径写进文档」习惯，需求 FR-2）。

### 16.5 核心实现细节 / 算法（`internal/service/valuation.go`）

**新增常量**

```go
const valFCFCustom = "custom"
const valFCFCustomMaxYuan = 1e14 // 换算后金额上限（Q4）

// 单位 → 元 的精确整数系数
var valFCFCustomUnits = map[string]int64{"yuan": 1, "qian": 1e3, "wan": 1e4, "yi": 1e8}

// valFCFModeNames 增补：valFCFCustom: "自定义"
```

#### 16.5.1 `ParseCustomFCF`（新增纯函数）

```go
// ParseCustomFCF 把用户录入的自定义基期现金流（原文 + 单位 key）精确换算为「元」。
// 校验顺序：单位合法 → 非空 → 十进制格式（≤2 位小数）→ >0 → ≤1e14 元。
func ParseCustomFCF(value, unit string) (float64, error)
```

实现要点：

1. `unit` 为空 → 取 `"yi"`（与参数缺省一致）；查 `valFCFCustomUnits`，未命中 → 错误「未知的基期现金流单位」。
2. `strings.TrimSpace(value)` 为空 → 「请输入基期现金流」。
3. 用正则 `^[0-9]+(\.[0-9]{1,2})?$`（或等价手写扫描，避免为此新增依赖——`regexp` 属标准库，可直接用）判定；不匹配 → 「基期现金流格式不正确（最多 2 位小数）」。该式天然拒绝负号、正号、字母、`1e5`、`.5`、`5.`、`1.234`。
4. **精确换算（避免浮点误差，推荐 `math/big.Rat`，标准库、无新依赖）**：
   ```go
   r, ok := new(big.Rat).SetString(s)                 // 精确解析十进制原文
   if !ok { /* 已被第 3 步拦截，作防御返回格式错误 */ }
   r.Mul(r, new(big.Rat).SetInt64(valFCFCustomUnits[unit])) // 精确 ×系数
   if r.Sign() <= 0 { return 0, errors.New("基期现金流需大于 0") }
   if r.Cmp(new(big.Rat).SetInt64(valFCFCustomMaxYuan)) > 0 {
       return 0, errors.New("基期现金流换算后金额过大（上限 100 万亿元）")
   }
   v, _ := r.Float64()                                 // 全流程唯一一次浮点化
   return v, nil
   ```
   - 用 `big.Rat` 保证「换算过程不四舍五入」（FR-3）：乘系数与比上限都在精确有理数域完成，只在**最后**转一次 `float64`（DCF 全链路本就是 `float64`，无法避免）。
   - **备选（更简单、误差 ≤1 ULP）**：按第 3 步正则先取整数与小数部分，拼成「百分位整数 ×100 的 int64」`k`，再 `float64(k)*float64(factor)/100`。因 `k` 与 `k×factor` 均在 int64 内可精确表示（`k×factor ≤ 1e16 < 2^63`），误差仅出现在最后的 `float64` 转换，对 1e14 量级 ≤0.01 元，实务可忽略。二选一均可，**推荐 `big.Rat`**（严格无舍入、代码更短）。
5. 本例 `6.5` + `yi` → `650000000`；`650000000` + `yuan` → `650000000`；`650000` + `qian` → `650000000`。

#### 16.5.2 `selectBaseFCF`（扩展 custom 分支）

```go
func selectBaseFCF(fcfByYear map[int]float64, years []int, mode string, n int, customValue float64) (float64, string, []int, error)
```

- **新增分支置于函数最前**（早于 `len(years)==0` 守卫，见 16.5.4）：
  ```go
  if mode == valFCFCustom {
      return customValue, valFCFModeNames[valFCFCustom], nil, nil // usedYears=nil → 不产生「取 X 年」提示
  }
  ```
- 其余逻辑（latest/average/median/trim_mean）**逐行不变**。
- 采用「扩展 `selectBaseFCF`」而非「在 `ComputeValuation` 里加 `if`」，理由：把「基期 FCF 的来源分发」收敛到单一函数，`mode` 覆盖完整（`valFCFModeNames` 仍是唯一名称源），且 custom 分支可被单测直接覆盖（16.8）。**备选**：在 `ComputeValuation` 内 `if params.FCFMode == valFCFCustom { ... } else { selectBaseFCF(...) }`，签名不动、改动更局部，代价是 dispatch 分散在两处、custom 分支需经 `ComputeValuation` 才能测。
- **签名变更需同步** `valuation_test.go:279-322` 的全部 `selectBaseFCF(...)` 调用点补第 5 参与 `ComputeValuation` 调用处。

#### 16.5.3 `ComputeValuation`（仅两处最小改动）

1. 调用点加参：`selectBaseFCF(fcfByYear, cfYears, params.FCFMode, params.FCFYears, params.FCFCustomValue)`。
2. 研发叠加块（`:107-111`）与 `fcf<=0` 守卫（`:112-114`）**位置和写法完全不变** → 自定义模式下 `fcf = FCFCustomValue + rdAdj`（FR-5：自定义值为基底、扩张额叠加其上），且 `FCFCustomValue ≤ 0` 时仍走「基期经营资产自由现金流为负或零，现金流贴现法不适用」（FR-4 后端兜底）。
3. 结果回填：`FCFYears` 仅对 average/median/trim_mean 赋值（既有 `switch` 不变）→ custom 得到 `0`（`omitempty` 不输出）；`FCFModeName` 来自 `valFCFModeNames[valFCFCustom]` = 「自定义」；新增 `FCFCustomValue`/`FCFCustomUnit` 回显（custom 时填、其余留零值）。
4. **不新增 `Notes`**：FR-7 的说明文案由前端 `val-desc` 承载；`Notes` 现有渲染是 warning 级 `el-alert`（前端结果区 `v-for`），自定义属正常输入而非告警，写进 `Notes` 会造成语义与视觉误导。**备选**：如需 API 自描述，可加一条中性 Note，但须同时调整前端 Notes 的呈现（超出本期范围）。

#### 16.5.4 边界与降级（Q5 相关）

- **不解耦报表**：`fcf_mode=custom` 仍要求 `year != 0`（`ComputeValuation:73-92` 的年份解析不变）——金融资产、长期股权投资、有息债务、研发扩张额本就来自报表。
- **custom 不依赖现金流表**：因 custom 分支早于 `selectBaseFCF` 的 `len(years)==0` 守卫返回，故某股票若资产负债表/利润表有年报但现金流量表为空，custom 模式仍能算（`year` 由任一表解析得到）。这比「强制要求现金流表」更稳健，且不违背 Q5（Q5 只要求「仍要求年报数据」，未要求三张表齐备）。**若要求三张表齐备**，把 custom 分支挪到守卫之后即可（更保守、但会把本可算的股票判为不支持）。
- 上年度研发数据缺失 → `rdExpansion` 返回 0 → custom 模式按自定义值计（FR-5 末条）。
- 报告期过滤（只取年报）沿用 `annualRows`，不涉及新增。

### 16.6 API 设计（`internal/api/handler.go`）

**路由不变**：`r.GET("/api/stock/:code/valuation", h.GetValuation)`（`router.go:19`）。

**`parseValuationParams` 改动**（`:312-330`，在既有 `DiscountRate<=0` 校验之后追加）：

```go
p.FCFMode = c.DefaultQuery("fcf_mode", "latest")
p.FCFYears = queryIntDefault(c, "fcf_years", 0)
p.AdjustRD = queryBoolDefault(c, "adjust_rd", false)
if p.DiscountRate <= 0 { return p, fmt.Errorf("折现率需大于 0") }

if p.FCFMode == "custom" { // 值与 service 层 valFCFCustom 对齐（与既有 "latest" 字面量风格一致）
    v, err := service.ParseCustomFCF(c.Query("fcf_custom_value"), c.DefaultQuery("fcf_custom_unit", "yi"))
    if err != nil {
        return p, err // 立即返回，不拉报表（fail-fast，省一次冷启动）
    }
    p.FCFCustomValue = v
}
return p, nil
```

- 失败即 `code:1`（HTTP 200，`GetValuation:249-252` 既有分支），且**不发起**行情/报表拉取（自定义校验在拉数之前）。
- **向后兼容**：`fcf_mode` 非 custom 时**不读** `fcf_custom_*`，即使带脏值也被忽略；`fcf_years` 解析路径不变。
- **常量对齐**：`"custom"` 为字面量，与既有 `"latest"` 缺省字面量风格一致；备选是把 key 导出为 `service.FCFModeCustom` 以消除两面字面量漂移风险。

**handler 与 service 的边界**：参数解析/校验留在 api 层（`parseValuationParams` 负责「查参 + 调纯函数 + 转错误」），换算算法本身在 service 纯函数里——满足分层约定且换算逻辑可脱离 HTTP 单测。

#### 16.7.2 纯函数 `validateCustomFCF`（须加入 `setup()` 的 `return`，与 `resolveAdjustRD` 同处，`app.js:892`）

```js
// 自定义基期现金流校验：合法返回 ''，非法返回中文提示（FR-4）。与后端 ParseCustomFCF 同口径。
function validateCustomFCF(v, unit) {
  if (v == null || v === '') return '请输入基期现金流';
  const num = Number(v);
  if (!isFinite(num)) return '基期现金流格式不正确（最多 2 位小数）';
  if (num <= 0) return '基期现金流需大于 0';
  const factor = VAL_FCF_UNIT_FACTOR[unit] || 0;
  if (factor <= 0) return '未知的基期现金流单位';
  if (num * factor > VAL_FCF_MAX_YUAN) return '基期现金流换算后金额过大（上限 100 万亿元）';
  return '';
}
```

> 前端只做「非空 + 数值 + >0 + 超限」的**即时提示**；「≤2 位小数」「非数字」由 `el-input-number` 控件本身约束（`:precision="2"` 且不接受非数字），**粘贴/绕过**的极端输入由后端 `ParseCustomFCF` 兜底（需求第 4 节「安全」）。双端校验，前端提示友好、后端兜底可信。

### 16.9 R12 关键决策点 / 待确认项

1. **精度实现：`math/big.Rat`（推荐）vs 百分位 int64**。`big.Rat` 严格无舍入、标准库、代码短；int64 方案更快但 1e14 量级存在 ≤0.01 元转换误差。需求明确「换算不四舍五入」，**推荐 `big.Rat`**；若 coder 倾向极简实现，int64 方案亦可接受（误差远小于业务意义）。
2. **`selectBaseFCF` 签名增参（推荐）vs `ComputeValuation` 内分支**。前者把「基期来源分发」收敛一处、custom 分支可直接单测，代价是既有测试 5 处调用点需补参；后者零签名改动但 dispatch 分散。**推荐前者**（与需求「自定义即第 5 种选取方式」的语义一致）。
3. **custom 是否要求现金流表齐备**。本设计让 custom 分支早于 `len(cfYears)==0` 守卫返回，故现金流量表为空但另有年报时**仍可算**（更稳健，且不违反 Q5）。若产品希望「三张表齐备才算」，把分支挪到守卫之后即可。**推荐当前方案**，并在 `docs/R4-公司股票估值/公司股票估值.md` 备注一句。
4. **`"custom"` 字面量 vs 导出常量**。handler 现以字面量 `"latest"` 作缺省，本设计沿用字面量 `"custom"`；若担心前后端/跨文件字面量漂移，可导出 `service.FCFModeCustom` 供 handler 引用。**推荐沿用字面量**（与现状风格一致，改动最小）。
5. **是否给 custom 写后端 `Notes`**。`Notes` 现渲染为 warning 级 `el-alert`，自定义属正常输入；本设计**不加** `Notes`，FR-7 说明文案由前端 `val-desc` 承载。若后续要 API 自描述，需同时下调 Notes 的告警级别（本期不做）。
6. **换行策略为全局、非仅移动端（已实测确认）**。`flex-wrap` 规则**不放在断点内**：除 `≤768px` 单列（可用宽 264px）外，**桌面 856–1065px 区间的 `.val-fields` 列宽仅 240–310px**，同样容纳不下 `92+8+130+8+72=310`，必须依赖同一换行规则（列宽 240 → 输入框压到 120 与它行对齐；254.7–309.7 → 输入框 130、单位下拉换第二行；310/328 → 单行逐像素不变，见 16.7.5 对照表）。若把 `flex-wrap` 只写在 `@media (max-width:768px)` 内，会漏掉这一桌面区间导致横向溢出。tester 已复算确认，不影响接口契约。
7. **`el-input-number` 加 `:controls="false"` 的宽度复核**。取消步进按钮后左右内边距变化，`--val-input-w` 130px 下可显示字符数增加，不影响对齐；若视觉上留白偏大，可微调自定义行的输入框宽度（仅展示层，无接口影响）。
8. **前端与后端校验口径的单一真值源**：`VAL_FCF_UNIT_FACTOR`/`VAL_FCF_MAX_YUAN`（JS）与 `valFCFCustomUnits`/`valFCFCustomMaxYuan`（Go）为两处常量，需同步修改。已用同源注释标注；如需单源可改由后端在页面注入，属过度设计，**推荐两处常量 + 注释**（与项目 `--val-input-w` 等既有跨端约定同风格）。
