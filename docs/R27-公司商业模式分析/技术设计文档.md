## 1. 设计目标与影响面

### 1.1 目标

1. 模块四 `business_model` 按 R26 契约接入：独立提示词、独立解析、独立 finalize、独立缓存、独立触发；`all` 中自动加入取数并集与并发调用。
2. 九要素的名称、代号、释义、顺序、分组**全部由后端固定**；AI 只回填 `analysis / basis / level`。
3. 总分、评级、覆盖率、可评分要素数由后端纯函数一次性计算；AI 返回的任何 `score / rating / grade / total_score` 一律忽略。
4. 缺失/脏数据只影响商业模式模块，不拖垮其他模块；前端对旧结构安全降级。
5. 零新增接口、零新增外部数据源、零新增请求参数。

### 1.2 非目标

- 不改五维评分维度、评分口径、雷达图、财务模块提示词与结论结构。
- 不改行业模块、估值模块的提示词/解析/finalize/渲染。
- 不改估值参数确定性口径、DCF、基期 FCF、敏感性矩阵、估值历史。
- 不新增数据库/持久化、不做商业模式历史或排行榜。
- 不做跨模块一致性硬校验（沿用 R26 Q10 的既定取舍）。
- 不新增九维雷达图，不做逐卡片入场动画。

### 1.4 兼容性结论

- **HTTP 接口无结构性变化**：路由、查询参数、响应包络 `{code, data, message}` 不变；`module=business_model` 由「尚未上线」变为正常分析；`all` 的 `modules` 多一个 `business_model` 条目。
- **缓存主动失效**：`aiCacheSchema` 升 `r27`，r26 旧缓存不再命中；无迁移。
- **模型层纯增量**：新增类型不改变既有结构体字段；`AIModuleInput` 新增内部字段（所有现有字面量均为 keyed，编译不受影响）。
- **前端本地缓存**：key 维度已含 `module`，无需新增；旧结果缺字段时按空/占位渲染。

## 2. 总体架构

### 2.1 分层与调用链

```text
前端 app.js（商业模式卡片）
  └─ GET /api/stock/:code/ai-analysis?module=business_model[&startYear&endYear]
       （或顶部「一键全分析」module=all，自动包含模块四）

api.GetAIAnalysis（internal/api/ai.go:62）
  ├─ ResolveAIModules(module) → 注册表（internal/service/ai_modules.go:67）
  ├─ 逐模块 peek 缓存（仅未命中模块参与 needs 并集）
  ├─ buildAIModuleData（internal/api/ai.go:240）
  │    ├─ FetchQuote
  │    ├─ fetchAnalysisReports（cfPageSize/bsPageSize）
  │    ├─ FetchSegmentIncome（失败降级为空）
  │    ├─ FetchIndustry（报表行无行业字段时回退 DMSK）
  │    ├─ ComputeAnalysis（六维指标）
  │    └─ FinancialLikeFromReports(income) → AIModuleInput.FinancialLike
  ├─ runAIModule（internal/api/ai.go:211）
  │    ├─ BuildBusinessModelPrompt
  │    ├─ DeepSeek.Chat（1 次，temperature=0，json_object）
  │    ├─ ParseAIBusinessModelResult（宽容解析，固定顺序，AI 评分丢弃）
  │    └─ FinalizeBusinessModelResult（后端汇总评分/评级/覆盖率/一致性）
  └─ 缓存 *model.AIBusinessModelResult，返回 AIModuleResponse

service 层：纯函数（提示词、解析、评分聚合、finalize）
client 层：唯一 IO（东财/腾讯/DeepSeek）
model 层：标准结构体
```

### 2.2 模块四注册项

在 `internal/service/ai_modules.go` 的 `aiModuleSpecs` 第 4 项落地：

```go
{
    ID: model.AIModuleBusinessModel, Title: "商业模式分析",
    Description: "九要素框架与商业模式评分",
    Implemented: true,
    // 六维指标需要三表；行业名用于提示词适配；不依赖 Growth/Peers/ValuationBase。
    Needs: AIModuleNeeds{
        Quote: true, Reports: true, Segments: true, Analysis: true, Industry: true,
    },
    BuildPrompt: BuildBusinessModelPrompt,
    Parse:       func(raw, _ string) (any, error) { return ParseAIBusinessModelResult(raw) },
    Finalize:    FinalizeBusinessModelResult,
},
```

**Needs 说明与「不新增取数」结论**

| 依赖 | 是否必要 | 理由 |
| --- | --- | --- |
| `Quote` | 是 | 公司名/代码/总市值进入用户消息头。 |
| `Reports` | 是 | `ComputeAnalysis` 必须先有三表；`FinancialLike` 也由利润表年报行判定。这不是新增数据源，只是复用财务/估值模块已在用的三表取数。 |
| `Segments` | 是 | 主营构成是九要素（尤其 CS/RS/CST）的核心事实。 |
| `Analysis` | 是 | 精简事实块（营收/毛利率/净利润/ROE/现金流/研发/资产结构）来自六维指标。 |
| `Industry` | 是 | 系统行业分类用于金融/周期/公用事业适配。 |
| `Growth` | 否 | 不需要一致预期/GDP/分红快照，避免额外外部请求。 |
| `Peers` | 否 | 不需要同行市值榜。 |
| `ValuationBase` | 否 | 不依赖估值模块的 AI 行业类型，避免跨模块耦合与额外计算。 |

- `all` 场景：财务模块已声明 `Reports/Segments/Analysis`、行业模块已声明 `Industry`，并集与 R26 完全相同，**不新增任何上游请求**。
- 单模块场景：使用现有 quote/三表/主营构成/DMSK 行业分类四类既有请求，**不新增数据源、不新增端点、不新增参数**。
- `FinancialLike` 从已取到的利润表行计算，不产生 IO。

### 2.3 模块位置与顺序

注册表顺序固定为 `financial → industry → valuation → business_model`，前端按注册表渲染。需求文档 §8.1 的「业务板块之后、相关公司之前」是 R26 拆分前的整包布局，已被 R26 取代；本文以模块四独立卡片为准。

### 3.2 九要素结果结构

```go
// AIBusinessElement 商业模式九要素之一。
// 名称/代号/分组/释义/顺序均由后端固定；AI 只回填 Analysis/Basis/Level。
type AIBusinessElement struct {
    Key        string `json:"key"`        // customer_segments 等固定 key
    Name       string `json:"name"`       // 客户细分
    Code       string `json:"code"`       // CS
    Group      string `json:"group"`      // customer / enterprise
    Definition string `json:"definition"` // 一句固定释义，≤30 字
    Order      int    `json:"order"`      // 1-9，固定顺序
    Level      string `json:"level"`      // strong/good/medium/weak/poor/unknown
    LevelName  string `json:"level_name"` // 强/良/中/弱/差/无法判断
    Analysis   string `json:"analysis"`   // ≤80 字；unknown 时为固定占位
    Basis      string `json:"basis"`      // ≤30 字；unknown 时为空
}

// AIBusinessModelResult 商业模式模块载荷。
type AIBusinessModelResult struct {
    Scored     bool                `json:"scored"`     // 可评分要素是否 ≥6
    Score      int                 `json:"score"`      // 0-100；Scored=false 时为 0
    Rating     string              `json:"rating"`     // 优秀/良好/一般/偏弱/较差；未评分时为空
    Summary    string              `json:"summary"`    // 一句话结论，≤40 字
    Conclusion string              `json:"conclusion"` // 总体归纳，≤300 字
    Coverage   int                 `json:"coverage"`   // 可评分要素数 0-9
    Total      int                 `json:"total"`      // 恒为 9
    Elements   []AIBusinessElement `json:"elements"`   // 恰好 9 项，固定顺序
    Evidence   string              `json:"evidence,omitempty"` // 轻量财务印证提示（不改变分数）
}
```

设计取舍：

- `Score int + Scored bool`：避免指针与 0 分混淆；前端只在 `scored === true` 时展示大号总分与评级，否则展示「信息不足，暂不评分」。
- 不输出单要素映射分数：防止伪精度，分档文字才是主信息。
- `Level` 用 ASCII canonical key，`LevelName` 用中文；前端用 `level` 找 CSS 类，用 `level_name` 做文字标签，颜色之外始终有文字。

### 3.3 九要素固定定义（后端唯一来源）

`internal/service/ai_business_model.go` 内置：

| Order | Key | 名称 | 代号 | Group | 固定释义（≤30 字） |
| --- | --- | --- | --- | --- | --- |
| 1 | `customer_segments` | 客户细分 | CS | customer | 为谁创造价值，目标客户群体是谁 |
| 2 | `value_propositions` | 价值主张 | VP | customer | 为客户解决什么核心问题，凭何被选择 |
| 3 | `channels` | 渠道通路 | CH | customer | 通过什么方式触达客户并传递价值 |
| 4 | `customer_relationships` | 客户关系 | CR | customer | 与客户建立和维持什么样的关系 |
| 5 | `revenue_streams` | 收入来源 | RS | customer | 如何从各客户群体获取收入 |
| 6 | `key_resources` | 核心资源 | KR | enterprise | 支撑模式运转的关键资产与能力 |
| 7 | `key_activities` | 关键活动 | KA | enterprise | 必须做好的最关键事项 |
| 8 | `key_partners` | 关键合作伙伴 | KP | enterprise | 哪些外部伙伴让模式更高效 |
| 9 | `cost_structure` | 成本结构 | CST | enterprise | 主要成本构成及固定/可变属性 |

**CS / CST 消歧（硬约束）**：`客户细分（CS）` 与 `成本结构（CST）` 是两个不同要素，不得混淆或合并。后端以固定 `key` 识别，**不依赖 AI 返回的名称字符串**；AI 返回名称不参与展示。

### 4.2 金融类判定

现有 `isFinancialLike`（`internal/service/valuation_recommend.go:1773-1775`）已是全项目口径：

```go
func isFinancialLike(income model.ReportRow) bool {
    return revenue(income) > 0 && v0(income, "OPERATE_COST") == 0
}
```

R27 只增加一个导出包装，供 api 层使用：

```go
// FinancialLikeFromReports 取最新年报行，复用 isFinancialLike 口径。
// 无年报行返回 false（模块此时通常会因年报表取数失败而失败）。
func FinancialLikeFromReports(income []model.ReportRow) bool {
    byYear, years := annualRows(income) // analysis.go:1943，已按年升序
    if len(years) == 0 {
        return false
    }
    return isFinancialLike(byYear[years[len(years)-1]])
}
```

- `annualRows` 已过滤非年报（报告期以 `12-31` 结尾），与全项目「静态估值只取年报」约定一致。
- 不修改 `isFinancialLike` 本身，估值口径零回归。

### 4.3 行业类型（cyclical / general / utility）的处理

**核实结论**：当前代码没有「行业名 → cyclical/general/utility」的后端确定性分类。`ValuationRecommendInput.IndustryType` 是 AI 在估值模块中给出的原始串（`valuation_recommend.go:147`），预推导阶段为空；`RecommendValuation` 内部只做白名单归一化（`:1429`），不会从行业名推断。因此：

- 若模块四依赖 `Rec.IndustryType`，要么需要 `ValuationBase=true`（触发估值预推导与增长快照取数），要么拿到的是缺省 `general`，且会与估值模块耦合。
- 本设计**不依赖估值模块**。用户消息中给出 `IndustryName`、`FinancialLike` 与营收/利润序列，由提示词要求 AI 自行判断「周期/公用事业/一般/金融」并选择相应分析口径；金融类另有后端确定性标记兜底。这样既满足 FR-4 的适配意图，又不新增取数、不引入跨模块耦合。

### 6.2 评分聚合（纯函数）

```go
// BusinessModelScore 后端确定性评分结果。
type BusinessModelScore struct {
    Scored   bool
    Score    int
    Rating   string
    Coverage int
    Total    int
}

// AggregateBusinessModelScore 等权平均、四舍五入、评级、覆盖率。
// 入参为 canonical level key；unknown/非法值不计分、不计入分母。
func AggregateBusinessModelScore(levels []string) BusinessModelScore {
    sum, scored := 0, 0
    for _, level := range levels {
        if s, ok := businessLevelScores[level]; ok {
            sum += s
            scored++
        }
    }
    total := businessTotalElements
    if scored < businessMinScored {
        return BusinessModelScore{Scored: false, Score: 0, Rating: "", Coverage: scored, Total: total}
    }
    score := int(math.Round(float64(sum) / float64(scored)))
    return BusinessModelScore{Scored: true, Score: score, Rating: businessRating(score), Coverage: scored, Total: total}
}

func businessRating(score int) string {
    switch {
    case score >= 90:
        return "优秀"
    case score >= 75:
        return "良好"
    case score >= 60:
        return "一般"
    case score >= 45:
        return "偏弱"
    default:
        return "较差"
    }
}
```

**算例（与需求 §7.3 一致）**

| 分档组合 | 计算 | 总分 | 评级 | 覆盖率 |
| --- | --- | ---: | --- | --- |
| 9 个强 | 9×95/9 | 95 | 优秀 | 9/9 |
| 9 个良 | 9×82/9 | 82 | 良好 | 9/9 |
| 5 强 + 4 中 | (5×95+4×68)/9 = 83.0 | 83 | 良好 | 9/9 |
| 6 强 + 3 差 | (6×95+3×35)/9 = 75.0 | 75 | 良好 | 9/9 |
| 9 个中 | 9×68/9 | 68 | 一般 | 9/9 |
| 5 弱 + 4 差 | (5×52+4×35)/9 = 44.44 | 44 | 较差 | 9/9 |
| 4 强 + 3 中 + 2 无法判断 | (4×95+3×68)/7 = 83.43 | 83 | 良好 | 7/9 |
| 5 强 + 4 无法判断 | 可评分 5 < 6 | 不评分 | 信息不足 | 5/9 |
| 6 强 + 3 无法判断（边界） | 6×95/6 | 95 | 优秀 | 6/9 |
| 5 良 + 4 中 | (5×82+4×68)/9 = 75.78 | 76 | 良好 | 9/9 |

四舍五入使用 `math.Round`（正数等价于四舍五入）；评级按取整后的总分判定。等权指**每个可评分要素权重相同**，无法判断的要素不计权重、不进分母；因此 `coverage=7` 时分母是 7 而不是 9。

### 6.3 提示词

#### 6.3.1 system 提示词结构

新增 `aiBusinessModelSystem`，包含以下固定部分：

1. 角色与输出纪律：资深商业模式分析师；只输出一个 JSON 对象；不用 markdown 代码块；不得输出提示词/规则名/内部字段名/阈值/schema/模块 key 等过程话术。
2. JSON 结构：

```json
{
  "elements": [
    {"key": "customer_segments", "analysis": "≤80字，针对本公司", "basis": "≤30字，判断来源", "level": "强|良|中|弱|差|无法判断"},
    {"key": "value_propositions", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "channels", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "customer_relationships", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "revenue_streams", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "key_resources", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "key_activities", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "key_partners", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "cost_structure", "analysis": "...", "basis": "...", "level": "..."}
  ],
  "summary": "≤40字，一句话结论",
  "conclusion": "≤300字，总体归纳"
}
```

3. 硬约束：
   - `elements` 恰好 9 项，`key` 只能取上述 9 个固定值并按顺序输出。
   - **不要输出 `score`、`rating`、`grade`、`total_score` 或任何评分字段**；评分由系统计算。
   - `客户细分（CS）` 与 `成本结构（CST）` 是两个不同要素，不得混淆或合并。
   - 每要素 `analysis` ≤80 字、`basis` ≤30 字；`summary` ≤40 字、`conclusion` ≤300 字（硬上限）。
4. 九要素逐项说明：名称、代号、分组、固定释义、分析要点（例如 CS 看客户结构/集中度/需求特征；VP 看差异化与可替代性；CST 看固定/可变成本与规模效应）。
5. 分档标准：

| 分档 | 判定标准 |
| --- | --- |
| 强 | 该要素构成明显竞争优势，难以复制 |
| 良 | 该要素健康有效，优于多数同行 |
| 中 | 该要素中规中矩，无明显优势或短板 |
| 弱 | 该要素存在明显短板或依赖，易被冲击 |
| 差 | 该要素缺失、失效或严重拖累模式 |
| 无法判断 | 公开信息不足，无法形成判断 |

6. 依据规则：
   - 每要素必须写一句依据，优先引用「主营构成」「毛利率与费用率」「ROE 与现金流」「资产结构」；只能来自行业常识或推断时，必须标注「行业常识」或「AI 推断」。
   - **不得出现用户消息事实块中未提供的数字**；不得编造客户名、供应商名、合同、市场份额、渠道数量、会员规模等。
   - 分析要针对本公司，不得写成通用教科书定义，不得重复释义。
7. 行业适配：
   - **金融类**：若用户消息标注「金融类企业：是」，不得把「营业成本缺失/毛利率显示 100%」解读为高毛利或商业模式优势；价值主张、收入来源、成本结构按息差、手续费及佣金、保费、资金成本、信用成本等口径分析；细分数据不可得时允许判「无法判断」。
   - **周期类**：重点分析资源禀赋、成本曲线位置、产品同质化、价格周期对盈利模式的影响；不得把周期高点利润当作可持续竞争优势。
   - **公用事业**：重点分析特许经营/管制价格、资产重型特征、稳定现金流与资本开支的关系。
   - **多元集团/主业不清**：以营收占比最大的板块为主线，明确指出多元化对客户细分、渠道与成本结构的稀释，不得把不相关板块硬拼成统一模式。
   - **无清晰商业模式/早期公司**：允许多数要素判「无法判断」，不得为了凑分而编造。
8. 总体归纳规则：2-4 句，串起「创造价值 → 传递价值 → 获取价值」逻辑链；点出最核心护城河及其依托要素、最脆弱环节或最大风险；不得简单重复九要素原文；不得出现投资建议、目标价、买卖评级；不与财务模块的评分/结论相互引用或复述。
9. 一句话结论规则：≤40 字，点明「模式是否优秀 + 最核心原因」，不得含任何阿拉伯数字。

### 6.4 解析（宽容，AI 评分丢弃）

```go
// ParseAIBusinessModelResult 宽容解析商业模式模块。
// 仅顶层 JSON 非法时返回 error；其余缺失/脏类型/非法分档按「无法判断」占位。
func ParseAIBusinessModelResult(raw string) (*model.AIBusinessModelResult, error)
```

解析流程：

1. `stripJSONFence` 去除 markdown 围栏。
2. 顶层 `json.Unmarshal` 到 `map[string]json.RawMessage`；失败 → error（模块失败）。
3. 若顶层无 `elements` 但存在 `business_model` 对象，则解包该对象（容忍 AI 多包一层）。
4. 解析 `elements`：
   - 优先按数组 `[]json.RawMessage` 解析；失败则尝试按对象 `map[string]json.RawMessage`（key → 要素对象）解析；仍失败 → 空列表（全部占位）。
   - 每条用 `map[string]any` 宽松读取，单条脏类型只丢该条。
   - 识别 key：`normalizeBusinessElementKey(rawKey, rawName, rawCode)`：
     - 先精确匹配固定 key；
     - 再按中文名/代号模糊匹配（去空白、括号）；
     - `CS` 单独出现时若名称不含「成本」则按客户细分，若名称含「成本」则按成本结构；`CST` 直接匹配成本结构；无法识别则丢弃（**不按数组下标强配**，避免漏项后错位）。
   - 重复 key：**第一条生效**，后续忽略。
   - `level`：`normalizeBusinessLevel` 归一化；无法识别 → unknown。
   - `analysis`：非字符串或去空白后为空 → **该要素强制降为 unknown**（没有分析就不参与评分，避免「强档 + 信息不足」自相矛盾）；unknown 时置固定占位「公开信息不足，暂无法判断」；已知分档按 80 字截断。
   - `basis`：非字符串 → 空；按 30 字截断；unknown 时强制为空；已知分档但为空时补「AI 推断（未注明来源）」。
5. 按 `businessElementDefs` 固定顺序重组，缺失项补占位（level=unknown，analysis=固定占位，basis=""），保证恰好 9 项。
6. `summary` / `conclusion`：仅当值为字符串时读取；`summary` 按 40 字截断，`conclusion` 按 300 字截断。
7. 忽略 AI 的 `score/rating/grade/total_score` 等任何评分字段（不进入解析结构）。

```go
func normalizeBusinessLevel(raw string) string {

    // 中/中等/一般/medium → medium；弱/较弱/弱势/weak → weak；

    // 其余 → unknown
```

### 6.5 Finalize（后端汇总与一致性）

```go
func FinalizeBusinessModelResult(payload any, in AIModuleInput) (any, error) {
    res, ok := payload.(*model.AIBusinessModelResult)
    if !ok || res == nil {
        return nil, fmt.Errorf("商业模式模块结果类型无效")
    }
    // 1) 评分聚合
    levels := make([]string, 0, len(res.Elements))
    for _, e := range res.Elements {
        levels = append(levels, e.Level)
    }
    score := AggregateBusinessModelScore(levels)
    res.Scored, res.Score, res.Rating = score.Scored, score.Score, score.Rating
    res.Coverage, res.Total = score.Coverage, score.Total

    // 2) 数字白名单（从同一事实块提取）
    fact := businessModelFactBlock(in)
    allowed := businessNumberWhitelist(fact)

    // 3) 要素依据/分析的数字守卫
    for i := range res.Elements {
        e := &res.Elements[i]
        if e.Level == model.BusinessLevelUnknown {
            continue
        }
        if !businessTextNumbersAllowed(e.Analysis, allowed) || !businessTextNumbersAllowed(e.Basis, allowed) {
            e.Basis = "AI 推断（含未核实数据）" // ≤30 字；分析文字保留，但依据明确标注
        }
    }

    // 4) 一句话结论：未评分/空/超长/含未提供数字/与评级矛盾 → 按评级默认句
    //    未评分（Scored=false）时固定为「可判断的信息不足，暂不评分。」，不保留 AI 的结论句。
    if !res.Scored || !businessSummaryValid(res.Summary, res.Rating, allowed) {
        res.Summary = businessDefaultSummary(res.Rating)
    }

    // 5) 总体归纳：空/超长/含未提供数字/含投资建议话术/与评级矛盾 → 确定性兜底
    if !businessConclusionValid(res.Conclusion, res.Rating, allowed) {
        res.Conclusion = businessConclusionFallback(*res)
    }

    // 6) 轻量财务印证提示（不改变分数）
    res.Evidence = businessFinancialEvidence(score, in.Analysis)

    log.Printf("AI 商业模式: scored=%v score=%d rating=%s coverage=%d/%d", res.Scored, res.Score, res.Rating, res.Coverage, res.Total)
    return res, nil
}
```

```go
// businessNumberWhitelist 从事实块文本中提取所有数字 token（regexp `\d+(?:\.\d+)?`），
// 并为小数补充整数部分（如 91.93 → 同时允许 91），降低格式差异导致的误报。
func businessNumberWhitelist(text string) map[string]bool

```

- 事实块本身是唯一数字来源；AI 引用数字时提示词要求保持事实块写法。

#### 6.5.2 一句话结论一致性

```go
func businessSummaryValid(summary, rating string, allowed map[string]bool) bool {
    // 0) rating 为空（未评分）→ false，强制使用「可判断的信息不足，暂不评分。」
    // 1) 非空、≤40 字
    // 2) 不含事实块之外的数字
    // 3) 不与评级矛盾：
    //    rating 为「一般/偏弱/较差」时，拒绝「非常优秀/卓越/极佳/顶级/完美/无懈可击」等强正向断言；
    //    rating 为「优秀/良好」时，拒绝「较差/糟糕/失败/不可持续/毫无竞争力」等强负向断言。
    // 不满足任一条 → false，由默认句替换。
}

func businessDefaultSummary(rating string) string {
    switch rating {
    case "优秀": return "模式优秀，核心优势突出且难以复制。"
    case "良好": return "模式清晰，核心优势可持续，但仍有改进空间。"
    case "一般": return "模式中规中矩，壁垒不明显，需持续观察。"
    case "偏弱": return "模式存在明显短板，抗风险与复制能力偏弱。"
    case "较差": return "模式缺乏可持续竞争力，价值获取能力较弱。"
    default:   return "可判断的信息不足，暂不评分。"
    }
}
```

> 评级由后端总分决定，AI 只给分档；因此「AI 写非常优秀但后端评级一般」时，以后端评级为准并丢弃该句，符合需求 §7.4。

#### 6.5.3 总体归纳兜底

- 空、超过 300 字、含未提供数字、含「目标价/买入/卖出/增持/减持/投资建议/评级」等投资建议话术，或与评级明显矛盾（复用 `businessSummaryValid` 的强正向/强负向关键词规则）→ 使用确定性兜底。
- 兜底句根据 `Scored/Rating` 与最强/最弱要素生成，例如：
  - 已评分：「九要素中，价值主张、核心资源相对突出；成本结构相对薄弱。整体商业模式评级为「良好」。」
  - 未评分：「公开信息不足，仅能对部分要素形成判断，暂不给出总体评分；已展示可判断要素的分析供参考。」
- 兜底句不含阿拉伯数字，≤300 字。

#### 6.5.4 财务印证提示（Q10）

```go
// businessFinancialEvidence 只用已有六维指标做一句提示，不改变分数。
// 规则（实现默认，可在单点调整）：
// - 未评分 → 空串。
// - 分数≥75，且（最新 ROE<8 或 近三年营收下降 或 经营现金流≤0）→
//     "模式判断偏乐观，建议结合 ROE 与经营现金流复核。"
// - 分数<60，且（最新 ROE≥15 且 经营现金流>0）→
//     "财务表现优于模式判断，需结合行业与竞争格局理解差异。"
// - 其余 → "财务数据与模式判断基本一致。"
func businessFinancialEvidence(score BusinessModelScore, a model.FinancialAnalysis) string
```

- 「近三年营收下降」用既有 `revenue` 指标最近至多 4 个年报值比较首末，仅用于提示，不新增指标。
- 提示文案不含数字，不影响评分、不进入缓存 key。

### 6.6 解析/finalize 失败边界

| 情况 | 处理 |
| --- | --- |
| 顶层 JSON 非法 | 模块失败（仅该模块；`all` 中其他模块不受影响） |
| `elements` 缺失/非数组/非对象 | 9 项全部「无法判断」占位，模块成功 |
| 单个要素类型异常 | 该要素按「无法判断」处理，其余保留 |
| 分档值非法 | 该要素按「无法判断」 |
| 分档已知但 analysis 为空 | 该要素强制降为「无法判断」，不参与评分 |
| AI 返回总分/评级 | 忽略，用后端聚合 |
| 可评分要素 <6 | `Scored=false`、`Score=0`、`Rating=""`；九要素照常返回 |
| AI 写了未提供数字 | 依据标注「AI 推断（含未核实数据）」；summary/conclusion 按规则兜底 |
| 要素 `basis` 为空 | 已知分档补「AI 推断（未注明来源）」；unknown 保持空 |

```js
// 保持后端固定顺序，只做分组过滤；旧结构缺 group 时按固定 5/4 下标兜底。
function businessElementsOf(result, group) {
  const list = result && Array.isArray(result.elements) ? result.elements : [];
  const grouped = list.filter(e => e && e.group === group);
  if (grouped.length || list.some(e => e && e.group)) return grouped;
  return group === 'customer' ? list.slice(0, 5) : list.slice(5, 9);
}

function businessOrderLabel(element, index) {
  const n = element && element.order ? element.order : index + 1;
  return String(n).padStart(2, '0');
}
```

## 8. 一致性设计

### 8.1 模块内一致性

- 总分、评级、覆盖率、`scored` 全部由同一个 `AggregateBusinessModelScore` 一次算出；前端不二次计算。
- 评级严格由取整后的总分映射；一句话结论在 finalize 中做「与评级矛盾」校验，矛盾则用默认句。
- 总体归纳做长度、数字来源、投资建议话术校验；不满足则用确定性兜底。
- 九要素分档与总分同源，不存在两套口径。

### 8.2 与财务模块「总体结论」的一致性

- R26 已把四个模块拆为独立 LLM 调用；按 R26 Q10 的既定取舍，**不做跨模块一致性复核**。
- R27 不修改财务模块提示词（遵守「R26 三模块不回归」）。商业模式提示词明确要求总体归纳只聚焦商业模式，不复述财务评分或结论。
- 前端不合并两处文案；若两处表述有差异，以商业模式板块的结构化结论与评分为准（需求 FR-5 / AC-16 的推荐口径）。
- 若后续需要硬一致，可另立需求在财务模块提示词中加一句「商业模式只做一句定性呼应」，本期不做。

### 8.3 与行业/业务板块模块的边界

- 商业模式引用同一份主营构成，但不复制行业模块的「前景/风险」原文；提示词要求针对「如何组成一套赚钱逻辑」分析。
- 相关公司名单不搬进九要素；如引用上下游角色，只做定性描述并标注「AI 推断」。

### 8.4 输出洁净

- 不输出提示词、规则名、内部字段名、阈值、权重、映射表、schema、模块 key。
- 免责声明固定为「AI 生成 + 系统汇总、仅供参考、不构成投资建议」。
- 依据中的「行业常识/AI 推断」必须可见。

## 附录 A：九要素提示词骨架（供 coder 直接展开）

```text
你是资深商业模式分析师。你将收到一家 A 股上市公司的公司信息、系统行业分类、主营构成与商业模式相关财务事实块。
请用九要素框架分析该公司如何创造价值、传递价值、获取价值，并只输出一个 JSON 对象（不要解释，不要用 markdown 代码块包裹）。

## 输出 JSON 结构（严格遵守，字段名与类型固定）
{
  "elements": [
    {"key": "customer_segments", "analysis": "≤80字，针对本公司", "basis": "≤30字，判断来源", "level": "强|良|中|弱|差|无法判断"},
    {"key": "value_propositions", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "channels", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "customer_relationships", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "revenue_streams", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "key_resources", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "key_activities", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "key_partners", "analysis": "...", "basis": "...", "level": "..."},
    {"key": "cost_structure", "analysis": "...", "basis": "...", "level": "..."}
  ],
  "summary": "≤40字，一句话结论",
  "conclusion": "≤300字，总体归纳"
}

说明：elements 必须恰好 9 项，key 只能用上述 9 个固定值并按顺序输出；不要输出 score、rating、grade、total_score 或任何评分字段，评分由系统计算。
客户细分（CS）与成本结构（CST）是两个不同要素，不得混淆或合并。

## 九要素与固定释义
1. 客户细分（CS，customer_segments）：为谁创造价值，目标客户群体是谁
2. 价值主张（VP，value_propositions）：为客户解决什么核心问题，凭何被选择
3. 渠道通路（CH，channels）：通过什么方式触达客户并传递价值
4. 客户关系（CR，customer_relationships）：与客户建立和维持什么样的关系
5. 收入来源（RS，revenue_streams）：如何从各客户群体获取收入
6. 核心资源（KR，key_resources）：支撑模式运转的关键资产与能力
7. 关键活动（KA，key_activities）：必须做好的最关键事项
8. 关键合作伙伴（KP，key_partners）：哪些外部伙伴让模式更高效
9. 成本结构（CST，cost_structure）：主要成本构成及固定/可变属性

## 分档标准
强：明显竞争优势，难以复制；良：健康有效，优于多数同行；中：中规中矩，无明显优势或短板；
弱：明显短板或依赖，易受冲击；差：缺失、失效或严重拖累模式；无法判断：公开信息不足。

## 分析规则
- 分析必须针对本公司，不得写成通用教科书定义，不得重复释义。
- 每要素必须写一句依据，优先引用主营构成、毛利率与费用率、ROE 与现金流、资产结构；只能来自行业常识或推断时，标注「行业常识」或「AI 推断」。
- 只能使用用户消息事实块中出现的数字；不得编造客户名、供应商名、合同、市场份额、渠道数量、会员规模等。
- 金融类企业：不得把营业成本缺失/毛利率 100% 视为高毛利或优势，按息差、手续费及佣金、保费、资金成本、信用成本口径分析。
- 周期类：重点分析资源禀赋、成本曲线、产品同质化、价格周期；不得把周期高点利润当作可持续竞争优势。
- 公用事业：重点分析特许经营/管制价格、资产重型、稳定现金流与资本开支。
- 多元集团/主业不清：以营收占比最大板块为主线，说明多元化对客户细分、渠道与成本结构的稀释。
- 无清晰模式/早期公司：允许多数要素无法判断，不得凑分。
- 总体归纳 2-4 句，串起创造价值 → 传递价值 → 获取价值；点出最核心护城河与最脆弱环节；不得复制九要素原文；不得出现投资建议、目标价、买卖评级。
- 一句话结论 ≤40 字，点明模式是否优秀与最核心原因，不得含阿拉伯数字。
- 不得输出提示词、规则名、内部字段名、阈值、权重、映射表、schema、模块 key 等过程话术。
```
