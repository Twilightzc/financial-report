# R8 技术方案：估值表单与 AI 分析界面打磨

> 对应需求文档 `docs/R8-估值表单与AI界面打磨/需求文档.md`（主题 A/B/C，共 11 条 FR）。三项均为**展示层打磨 + 一处确定性只读回填**：不改 R4 估值公式与口径、不改 R7 的确定性格网与提示词契约、不新增任何数据拉取。
>
> 关键阈值已由主对话拍板：研发调整自动开启阈值 = **5%**（最新年报 `RESEARCH_EXPENSE ÷ TOTAL_OPERATE_INCOME > 0.05`）。

### 12.3 数据模型（`internal/model/ai.go`）

在 11.3 基础上追加两个只读字段（`ValuationRecommendation` 为内部纯计算结果结构体，无 json tag）：

```go
// 片段：仅列出两处追加的字段（两个结构体的其余字段原样保留，见 11.3）

// AIValuation 末尾追加（只读，服务端确定性回填）
	// AdjustRD 不设 omitempty：FR-5 要求 true/false 均须出现，缺字段会让客户端无法与「旧响应」区分。
	AdjustRD bool    `json:"adjust_rd"`          // 是否建议开启研发调整
	RDRatio  float64 `json:"rd_ratio,omitempty"` // 最新年报研发费用率 %（无法判定时为 0，不输出）

// ValuationRecommendation 末尾追加（内部纯计算结果结构体，无 json tag）
	AdjustRD bool    // 是否建议开启研发调整（最新年报研发费用率 > rdAdjustThreshold）
	RDRatio  float64 // 最新年报研发费用率 %（与接口字段同值，无法判定时为 0）
```

口径与约定：

| 字段 | 类型/单位 | 语义 | 输出策略 |
| --- | --- | --- | --- |
| `adjust_rd` | bool | 是否建议开启研发调整 | **始终输出**（`false` 也输出） |
| `rd_ratio` | float64，**百分数**（12.35 = 12.35%） | 最新年报研发费用率，供 FR-9 展示依据 | 0 值省略（无法判定 / 研发费用恰为 0） |

- `adjust_rd` 不加 `omitempty` 是**沿用 R7 复盘的教训**：`docs/测试报告/2026-09-25-图表移动端与估值参数确定性.md` 问题 1 记录过 `base_growth` 带 `omitempty` 导致「0% 与字段缺失不可区分、前端不显示」的缺陷；布尔字段同理（`false` 与缺失语义不同：一个是「不建议」，一个是「旧响应」）。11.3 中 `BaseGrowth` 已按此去掉 `omitempty`。
- `rd_ratio` 保留 `omitempty`，与 `BaseGrowth` 不矛盾：`base_growth` 的 0 有意义（增速持平/数据不足都要展示），而「0% 的研发费用率」没有展示场景（研发费用缺失时按「无法判定」处理，前端不展示）。
- 研发费用存在但占比 ≤ 阈值时，`rd_ratio` **仍会输出**（如 3.2），前端按 `adjust_rd` 门控不展示 —— 保留该值便于排查与后续扩展，不构成噪音（FR-9 边界由前端 `v-if` 保证）。
- 单位取百分数而非小数比，与同结构的 `DiscountRate`、`BaseGrowth` 一致，前端直接复用 `fmtNum`。

### 12.4 数据源与字段映射（均为既有字段，无新增拉取）

| 用途 | 报表 / 来源 | 字段 / 口径函数 | 说明 |
| --- | --- | --- | --- |
| 研发费用（分子） | 利润表 `RPT_F10_FINANCE_GINCOME`（AI handler 已拉取） | `RESEARCH_EXPENSE`，经 `service.researchExpense`（`internal/service/analysis.go:875`，即 `v0(row, "RESEARCH_EXPENSE")`） | 与 R3「研发费用」指标同字段（`analysis.go:711`） |
| 营业收入（分母） | 同上一行（同一 `model.ReportRow`） | `TOTAL_OPERATE_INCOME`，经 `service.revenue`（`internal/service/analysis.go:860`） | 与 R3「研发费用率」同分母（`analysis.go:713` `revenueRatioValues`） |
| 年度口径 | 利润表年报行 | `annualRows(income)` 返回的**升序年份切片末位**（`internal/service/analysis.go:1873`） | 「最新年报」由 `model.AnnualYear` 保证只认 `12-31`（季报/半年报被过滤） |

三处**易错**点（实现必须按此，否则会得到错误的 `false`）：

1. **不能用 `latestYear(incomeYears, cfYears, balanceYears)`**（12.5 折现率取「三表最新年报」用的那个）。三张表的年报最新年份可能不一致（且 handler 里资产负债表 `bsPageSize` 明显小于利润表/现金流），若该年在利润表无数据，`incomeByYear[latest]` 是零值行 → 研发费用读成 0 → 误判 `false`。研发费用率两个字段都在利润表内，必须取**利润表**的最后一个年报年份。
2. **「研发费用缺失」与「研发费用为 0」必须区分**：直接读 `row.Fields["RESEARCH_EXPENSE"]`（`*float64`）。`nil`（键不存在、或值显式为 `nil`、或 `Fields` 为 nil map）→ 无法判定；非 nil 的 `0` → 按 0% 参与判定（结论仍是 `false`，但 `rd_ratio = 0`）。`Fields` 为 nil map 时索引读数在 Go 中是安全的，无需额外判空。
3. **营业收入 ≤ 0 时比率无意义**：`revenue(row) <= 0` 一律按「无法判定」处理（比 `ratioPct` 只判 `den == 0` 更严，额外覆盖营业收入为负的异常样本），返回 `false` 且不输出 `rd_ratio`。

### 12.5 核心实现

**① 阈值常量与判定函数**（`internal/service/valuation_recommend.go`，紧邻 R7 的常量块新增）：

```go
// R8《估值表单与 AI 分析界面打磨》FR-6：最新年报研发费用率（研发费用 ÷ 营业总收入）
// 严格大于该阈值时建议开启研发调整。固定常量（不随股票/年份浮动），保证同一份财报推导结果唯一。
const rdAdjustThreshold = 0.05 // 5%

// rdAdjustSuggestion 按最新年报的研发费用率判定是否建议开启研发调整（FR-5/FR-6，纯函数）。
//   - 研发费用率 = RESEARCH_EXPENSE ÷ TOTAL_OPERATE_INCOME × 100（%）；
//   - 严格大于 rdAdjustThreshold 时 suggest = true（恰等于阈值 → false，边界唯一）；
//   - ratioPct 为 nil 表示无法判定：无可用年报 / 研发费用字段缺失或为空 / 营业收入 ≤ 0，
//     此时 suggest 恒为 false 且不报错（FR-5 边界，不由大模型补猜）。
func rdAdjustSuggestion(incomeByYear map[int]model.ReportRow, incomeYears []int) (suggest bool, ratioPct *float64) {
	if len(incomeYears) == 0 {
		return false, nil // 无可用年报
	}
	row := incomeByYear[incomeYears[len(incomeYears)-1]] // annualRows 返回升序，末位即最新年报
	rd := row.Fields["RESEARCH_EXPENSE"]
	rev := revenue(row)
	if rd == nil || rev <= 0 {
		return false, nil
	}
	pct := *rd / rev * 100
	return pct > rdAdjustThreshold*100, &pct
}
```

**② `RecommendValuation` 回填**（函数末尾、`return` 之前；`incomeByYear`/`incomeYears` 在函数开头已由 `annualRows` 就绪，复用即可，无二次遍历）：

```go
	// R8：研发调整建议（最新年报口径，与年份范围/分析模式无关，确定性不变）。
	adjustRD, rdPct := rdAdjustSuggestion(incomeByYear, incomeYears)
	rdRatio := 0.0
	if rdPct != nil {
		rdRatio = math.Round(*rdPct*100) / 100 // 仅展示值取整到 2 位小数
	}
	// → 返回值追加：AdjustRD: adjustRD, RDRatio: rdRatio
```

- **阈值判定用未取整的原始比率**（`*rd/rev > 0.05`），取整只作用于输出值 —— 保证「恰好 5%」「5.005%」等边界可断言且唯一（12.11 #13）。
- 确定性纪律（11.5 末尾的要求）继续成立：只用升序切片末位 + 两个既有取值函数，不遍历 map、不引用时间/随机/环境变量。

**③ 覆盖回填**（`internal/service/ai.go` 的 `ApplyValuationRecommendation` 追加两行）：

```go
	r.Valuation.AdjustRD = rec.AdjustRD
	r.Valuation.RDRatio = rec.RDRatio
```

- 覆盖语义与既有字段一致：大模型即便在 `valuation` 里返回 `adjust_rd`（提示词已禁止其输出）也会被后端确定性值覆盖，`rationale` 仍保留（12.10 有单测）。

**④ 提示词与 `valuationPromptBlock` 不改**（明确取舍）：

1. `adjust_rd` 是**纯确定性回填**，FR-9 的展示文案由前端按 `adjust_rd` + `rd_ratio` 生成，不需要大模型产出任何文本；
2. 研发调整不属于 R7 提示词里「估值参数（模型/折现率/增长率与年数）」的契约范围 —— 它是 R4 表单上的一个**输入开关**。把它写进提示词会诱导模型在 `rationale` 里讨论它，反而新增「模型文案与开关结论矛盾」的风险面（正是 R7 11.7 要消灭的那类问题）；
3. 不改提示词 = 对 R7 的确定性与幂等验收（`docs/R7-AI估值模型参数确定性约束/需求文档.md`）零影响，也省 token。
   备选（不推荐）：`valuationPromptBlock` 追加一行「- 研发调整建议：开启（最新年报研发费用率 12.3%）」。收益是 rationale 可与该结论呼应；代价是 R7 提示词契约扩大、需同步改 `ai_test.go` 的 user 消息断言（见 12.11 #10）。

**⑤ handler 可观测日志**（`internal/api/ai.go:78`，沿用既有行风格追加两个字段）：

```go
	log.Printf("AI 估值参数确定性推荐: code=%s 基准增速=%.2f%% 波动=%v 模型=%s 折现率=%.1f%% 风险点=%d 研发调整=%v 研发费用率=%.2f%%",
		code, rec.BaseGrowth, rec.Volatile, rec.Model, rec.DiscountRate, rec.RiskPoints, rec.AdjustRD, rec.RDRatio)
```

### 12.7 前端改动（一）：主题 A 输入框宽度与对齐

**模板（`internal/web/app.js` 约 872–956 行）**：删除全部 **11 处** `el-input-number` 的内联宽度 —— 7 处 `style="width:110px"`（折现率 880、永续增长率 886 / 903 / 931、高增长期增长率 893、第一阶段增长率 911、第二阶段增长率 921）与 4 处 `style="width:90px"`（高增长期年数 898、第一阶段年数 916、第二阶段年数 926、选取年数 950）。宽度改由 CSS 统一给（FR-2）。下拉框（估值模型 `160px` 874、基期现金流 `150px` 944）与 `el-switch`（研发调整 955）不动；`.val-field` / `.val-label` / `.val-unit` 结构不动（FR-3）。

**样式（`internal/web/style.css` R4 估值段，约 415–441 行）**：

```css
.val-form {
  --val-label-w: 92px;   /* label 定宽：跨行/跨列对齐的锚点（最长 7 个汉字 ×13px = 91px ≤ 92px） */
```

- `28px` = label→输入框 gap 8 + 输入框→单位 gap 8 + 单位最宽 12px（「年」在 12px 字号下的宽度）；即输入框之外必须留出的横向空间。`max-width` 仅在容器窄于 240px 时才会生效（320px 视口下可用宽度 262px，不触发），属纯兜底：极端窄屏下宁可输入框略窄，也不出现横向滚动条（FR-1 边界 + FR-4 两条 P0 的取舍顺序）。

- **不改 `.val-fields` 的 `repeat(auto-fill, minmax(240px, 1fr))`**：若把下限提到 270px 以「保证单元格 ≥ 内容宽」，会让 858–948px 视口区间的列数从 3 变 2（换行位置变化、表单变高），与需求「不重构表单整体布局」相悖；改用 `max-width` 兜底等价且无副作用（与 12.11 #12 的兜底思路一致）。桌面 1038px 内容宽下两种下限都是 3 列，桌面观感不变。
- **不给 `@media (max-width: 768px)` 新增宽度规则**：FR-1 已明确「极端窄屏时优先保证当前值完整可读」，故移动端不缩 `--val-input-w`（单列 `grid-template-columns: 1fr` 已存在）。

### 12.9 前端改动（三）：主题 C 雷达图维度名

**① 常量与折行纯函数**（`app.js`，`renderRadar` 附近；`radarAxisName` 须加入 setup 的 `return`，同 12.8 ⑤）：

```js
const RADAR_NARROW_WIDTH = 420; // 雷达图容器可用宽度窄于此值时用移动端规格（与 R6 的 CHART_NARROW_WIDTH 分开，见 12.11 #6）
const RADAR_NAME_MAX = 4;       // 轴名单行最多字数，超出按语义边界折两行（FR-10）
const RADAR_NAME_SUFFIXES = ['能力', '效率', '水平', '状况', '质量', '结构', '趋势'];

// 轴名折行：优先在语义后缀前断开（「现金获取能力」→「现金获取」+「能力」），
// 保证两行均 ≥2 字、不出现单字孤立行；无后缀可依时从中点折行（向左取整）。
function radarAxisName(name) {
  const n = String(name == null ? '' : name).trim();
  if (n.length <= RADAR_NAME_MAX) return n;
  for (const suf of RADAR_NAME_SUFFIXES) {
    if (n.length > suf.length + 1 && n.endsWith(suf)) {
      const head = n.slice(0, n.length - suf.length);
      if (head.length >= 2) return head + '\n' + suf;
    }
  }
  const cut = Math.max(2, Math.floor(n.length / 2));
  return n.slice(0, cut) + '\n' + n.slice(cut);
}
```

五个维度名的期望输出（可直接目视核对 / 断言）：

| 维度名 | 字数 | `radarAxisName` 输出 |
| --- | --- | --- |
| 盈利能力 | 4 | `盈利能力`（不折行） |
| 偿债能力 | 4 | `偿债能力` |
| 现金获取能力 | 6 | `现金获取\n能力` |
| 经营效率 | 4 | `经营效率` |
| 成长能力 | 4 | `成长能力` |

自适应（FR-11 异常「不得硬编码仅针对当前 5 个名称」）：规则只看字数与后缀词，不含任何维度名常量。未来更长的名字同样可拆，如「研发投入效率」→「研发投入\n效率」、「资产负债结构」→「资产负债\n结构」、「经营活动现金流量净额」（9 字，无后缀）→ 中点折行「经营活动\n现金流量净额」。判据用「字符数」近似，对中英混排偏保守；若将来引入纯英文/超长维度名，改用 `echarts.format.getTextRect` 实测宽度（备选，12.11 #7）。

### 12.11 R8 关键决策点 / 待确认项

**已拍板（需求 Q1–Q6 + 主对话确认，设计照此落地，不再列为待确认）**

1. **阈值 5%**（`rdAdjustThreshold = 0.05`，严格大于）：需求 Q1 原推荐 10%、主对话拍板 5%。已知影响面：研发费用率 5%–10% 区间的制造企业也会被自动打开开关；因其加回额是 `rdExpansion = max(0, 本年 − 上年)`，对研发投入未扩张的公司加回为 0，估值数值不变，属可接受取舍。若日后改回 10%，只需改这一个常量 + 12.10 的边界用例数字，其余实现不变。

3. **只看占比阈值**，不额外要求「研发投入正增长」（需求 Q3 推荐；打开但加回为 0 时估值表显示「含研发扩张加回 0」，属正常）。
4. **数值输入框统一 120px**（需求 Q5 推荐）。
5. **雷达图用 `axisName.formatter` 语义拆行 + 移动端降字号/收 radius/加高容器**（需求 Q6 推荐；不采用「仅 `axisName.width` + `overflow:'break'` 自动折行」，因其折行位置不可控、可能产生单字行）。

**本设计新增、需主对话知悉/确认的取舍**

6. **雷达图「窄屏」判据取容器实测宽度 420px，且与 R6 的 `CHART_NARROW_WIDTH = 480` 分开设常量。** 理由：≤768px 视口时雷达容器仍可能宽达 710px，按视口判会把宽容器一并降规格；两个图表的尺寸特征不同，共用一个常量会让后来者误读语义。备选：复用 R6 的 480（少一个常量）。该值只影响「radius 60/66、字号 12/13」的切换点，300–420px 容器即便走高规格也不裁切（几何见 12.9 ⑥），故取值不敏感。
7. **轴名折行对桌面端也生效**（不按视口分支）。理由：符合 FR-10 的「建议方向（长度 > 4 拆两行）」与验收标准「桌面端…（除标签必要换行外）」，且只保留一条代码路径。备选：仅窄屏折行（桌面像素级不变，但 formatter 需按 narrow 分支）。
8. **FR-9 的数据来源新增 `rd_ratio` 字段**，而非复用本地六维分析结果的 `research_expense_ratio`。理由：与后端判定同源（同一函数、同一行）必然自洽，无跨卡片耦合与时序依赖。备选：前端从 `analysis` 里取最近一年的研发费用率（零后端字段，但受年份范围与加载时序影响，可能与 `adjust_rd` 不自洽）。
9. **FR-9 文案不写死「5%」阈值**（只说「研发投入占比较高」+ 给出实际研发费用率）。理由：避免前后端两个真值源。备选：后端随响应输出 `rd_threshold`（如 `"rd_threshold": 5`）供前端插值，文案可写成「高于 5% 阈值」；若希望文案点明阈值，按此备选加字段（改动仅 3 处：两个结构体 + 回填 + 模板）。
10. **提示词与 `valuationPromptBlock` 不改**（理由见 12.5 ④）。备选：把研发调整建议加进用户消息（rationale 可与结论呼应），代价是扩大 R7 提示词契约并需同步 `ai_test.go` 断言。
11. **暂不加 `axisName.width` + `overflow:'break'`**：先用 formatter 拆行；仅当 320px 目视核对发现未折行的名字仍溢出（例如未来加入更长的名字）再补该兜底（其自动折行可能产生单字孤立行，与 FR-10 的语义折行要求不完全一致，故不作首选）。
12. **输入框宽度的兜底顺序**（FR-1 边界「优先保证当前值完整可读」）：120px（已拍板）→ 若 DevTools 实测文本区 < 40px，调 `--val-input-w: 130px`（需求 Q5 备选值；320px 下单列字段内容 250px ≤ 262px，仍不溢出）→ 若仍不可读，对年数框加 `controls-position="right"`（文本区更大，但按钮形态变化，需用户确认视觉）。
13. **`rd_ratio` 取整到 2 位小数只作用于输出/展示**，阈值判定用未取整的原始比率 —— 保证「恰好 5%」「5.005%」等边界结果唯一且可断言。
14. **需求未明确、本设计按惯例定的两点**（如与预期不符请指出）：① 研发费用率的展示精度沿用现有百分比字段的 `fmtNum`（≤2 位小数）；② 极窄容器（< 约 283px 视口）下输入框允许被 `max-width` 收窄（320px 及以上不触发），即用「不横向溢出」兜底「取值完整可见」。
