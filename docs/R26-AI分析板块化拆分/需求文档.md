# AI 智能分析板块化拆分（模块化 + 各模块一键分析）

> 需求编号：R26
> 状态：需求分析完成，待用户确认 §12「待确认问题」（重点 Q1 接口形态、Q2 LLM 调用模型）后进入技术设计

> 口径说明：本文金额单位为亿元（特别注明除外）；比例写 `%`；评分 0-100。代码事实截至 2026-11-22。

## 1. 背景与目标

### 1.1 背景

现有「AI 智能分析」是一次请求产出全部内容：一次取数 + 一次 LLM 调用，返回五维评分与雷达图、总体结论、行业分析、业务板块、行业龙头、产业链/合作公司、估值参数推荐，前端在一个长面板里顺序渲染。

现状痛点：

1. **不可按需分析**：用户只想看估值参数或行业分析时，也必须等待全部内容生成，耗时与 token 成本无法节省。
2. **新增内容只能继续加长单次输出**：任何新板块都要塞进同一次调用、同一个 `max_tokens=8192` 预算与同一个长面板，输出截断风险与等待时间持续上升。
3. **模块边界不清**：字段散落在同一个结果结构里，新增/调整某类内容时难以界定影响面与回归范围。
4. **分析模式增加选择负担**：现有「简洁/标准/详细」需要用户预先判断，实际使用中用户几乎总是想看完整信息。

用户希望把 AI 分析拆成若干独立板块（模块），每个模块可单独「一键分析」，也可「一键全分析」并发触发全部模块；同时删除分析模式，统一输出详细内容。这样后续新增分析内容（例如 R27 商业模式）只需增加一个模块，不影响既有模块。

### 1.4 非目标

- 不改变任何分析内容、措辞规范、字段上限、评级口径与估值参数算法；只做结构拆分与去分析模式。
- 不新增外部数据源、不改变东财/腾讯取数接口、不改变 `cfPageSize`/`bsPageSize`、不改变年报过滤与年份范围规则。
- 不新增评分维度、不改五维雷达图、不让任何模块的评分参与 DCF 或估值计算。
- 不做分析结果持久化、历史记录、跨公司对比或排行榜。
- 不做 SSE/流式输出、不做逐模块实时推送（可作为后续增强，见 Q4）。
- 不重做 AI 板块以外的页面；不动三大报表、六维分析、公司价值、估值卡片与估值历史的既有交互。
- 不实现商业模式分析内容（由 R27 负责）；本需求只预留模块四的位置与契约。

## 2. 术语与模块定义

### 2.1 术语

- **模块（Module）**：一个可独立触发、独立返回、独立缓存的分析单元，拥有固定 key、标题、输入事实、提示词、输出结构与前端卡片。
- **模块结果**：该模块自己的输出载荷（字段集合见 §2.3），不包含其他模块字段。
- **一键分析**：模块卡片内的按钮，只触发本模块。
- **一键全分析**：AI 板块顶部的按钮，一次触发全部可用模块。
- **详细档**：原 `reasoning=high` 的内容详略标准；本需求起为唯一标准。
- **模块状态**：`idle`（未分析）/ `loading`（分析中）/ `ok`（成功）/ `error`（失败）/ `not_implemented`（模块未上线，仅 R26 的模块四）。

### 2.2 四个模块定义

| 顺序 | 模块 key（建议） | 模块名称 | 一句话职责 |
|---:|---|---|---|
| 1 | `financial` | 公司财务分析 | 只回答「财务健康与经营质量如何」：五维评分 + 总体结论 |
| 2 | `industry` | 行业分析 | 只回答「所处行业与业务、产业链位置如何」：行业分析 + 行业龙头 + 业务板块 + 相关公司 |
| 3 | `valuation` | 估值参数分析 | 只回答「估值参数如何取」：确定性估值参数推荐 |
| 4 | `business_model` | 商业模式分析 | 只回答「靠什么活着、怎么赚钱、能否持续」：R27 实现，本需求仅预留 |

模块 key 为前后端与缓存使用的稳定标识；中文名仅用于展示。R26 实现模块一至三，模块四不实现。

### 2.3 模块 ↔ 现有字段精确映射

| 模块 | 现有 `AIAnalysisResult` 字段 | 字段说明 | 归属结论 |
|---|---|---|---|
| `financial` 公司财务分析 | `scores[]` | 固定 5 项：盈利能力/偿债能力/现金获取能力/经营效率/成长能力，0-100 整数 + 一句话点评 | 只属于财务模块 |
| `financial` | `conclusion` | 总体结论（现有 5 段式：公司质地与商业模式、护城河、财务健康与盈利质量、风险隐忧、综合评级） | 只属于财务模块；口径见 Q3 |
| — | （前端雷达图） | 由 `scores` 派生，不是独立接口字段 | 跟随财务模块渲染 |
| `industry` 行业分析 | `industry{name, prospect, competition, application}` | 行业名称、前景、竞争格局、应用方向/需求 | 只属于行业模块 |
| `industry` | `leaders`（`LeaderBoard`） | 后端按东财行业分类 + 同行市值确定性回填，非 AI 输出；含行业名/本公司排名/0–3 家龙头 | 只属于行业模块 |
| `industry` | `businesses[]`（含每个板块的 `leaders`/`related`） | 业务板块名称、阶段、贡献、前景、风险；细分业务龙头与相关公司（AI 推断） | 只属于行业模块 |
| `industry` | `chain{upstream, downstream}` | 产业链上下游（AI 推断，各 0–3 家） | 只属于行业模块 |
| `industry` | `partners[]` | 合作/关联公司（AI 推断，0–3 家） | 只属于行业模块 |
| `valuation` 估值参数分析 | `valuation`（`AIValuation` 全部字段） | 模型、基期 FCF、折现率、增长参数、关键校验、警告、`rationale` 等；数值由后端确定性推导（R7/R19～R25），AI 只提供 `industry_type`/`company_risks`/`rationale` | 只属于估值模块 |
| `business_model` 商业模式分析（R27） | `business_model`（R27 新增） | 九要素 + 总体归纳 + 商业模式评分 | 只属于模块四；R26 不存在该字段 |
| 元数据 | `usage`（`TokenUsage`） | 本次大模型调用 token 用量 | 不归属模块；按模块各带一份，全分析再给合计 |

**字段归属原则（硬约束）**：

1. 每个字段**只在一个模块**的响应中出现，不跨模块复制；前端不得从其他模块推断本模块字段。
2. `industry.name`（行业模块）与 `valuation.industry_type`（估值模块）是两个不同字段：前者是行业展示名，后者是 `cyclical/general/utility` 估值分类；不得互相替代或合并。
3. `leaders` 始终是后端确定性数据，即使行业模块的 LLM 部分失败，也不得改由 AI 生成。
4. 模块内部字段名、类型、语义与现有结构完全一致，便于前端复用现有渲染片段与后端复用现有解析器。
5. 雷达图、评分条、行业龙头按钮、公司名称解析、估值参数折叠等既有交互能力不因拆分丢失。

### 2.4 模块输入与确定性计算（用于界定「零新增取数」）

| 模块 | 必需输入 | 后端确定性计算 | LLM 职责 | 可省略的输入 |
|---|---|---|---|---|
| `financial` | 公司名称/代码/总市值、三表、六维指标、主营构成 | `ComputeAnalysis`（六维指标） | 五维定性与打分、总体结论 | 增长快照、行业龙头、估值事实块（结论不引用估值数值） |
| `industry` | 公司名称/代码、总市值、主营构成、行业分类（报表行优先，缺失回退 DMSK）、同行市值榜 | `FetchIndustryPeers`（龙头榜）、`IndustryFromReportRows`/`FetchIndustry`（行业名） | 行业前景/竞争格局/应用方向、业务板块、产业链上下游、合作公司 | 六维指标全量序列、增长快照、估值参数、`ComputeAnalysis` |
| `valuation` | 公司名称/代码、总市值、三表、主营构成、增长快照 | `RecommendValuation` 两段式（预推导 → 读取 AI 的 `industry_type`/`company_risks` → 终态重算）、`ApplyValuationRecommendation` 覆盖回填 | 只输出 `industry_type`、`company_risks`、`rationale` | 六维指标全量序列（`ComputeAnalysis` 不必执行） |
| `business_model`（R27） | 主营构成、六维指标、估值事实块、行业名/行业类型、是否金融类 | R27 定义的评分汇总 | R27 定义 | R27 定义 |

- 上表是**数据依赖边界**：单模块请求只取该模块必需的数据；`module=all` 取各模块并集一次，再并发执行各模块，禁止对每个模块分别重复请求上游。
- 输入裁剪不得改变输出口径：若某字段的现有内容依赖被裁剪的输入，则保留该输入。技术设计需以「拆分前后同股票输出结构/约束一致」验证。
- 不新增数据源，不新增取数期数；主营构成拉取失败仍按「无主营构成」降级，不使模块整体失败（估值模块除外：其确定性参数依赖三表，三表失败则模块失败）。

## 3. 用户故事 / 使用场景

- 作为个人投资者，我只想快速看财务好坏与结论时，点击「公司财务分析」的「一键分析」，不必等待行业与估值内容，以便快速筛选。
- 作为研究者，我想单独刷新行业与产业链信息，点击「行业分析」即可得到行业、龙头、业务板块与相关公司，而不重复消耗财务评分与估值参数。
- 作为准备估值的用户，我点击「估值参数分析」只拿确定性的模型、折现率与增长参数，并自动套用到估值表单。
- 作为想一次看全的用户，我点击顶部「一键全分析」，三个模块同时开始分析，谁先完成都不影响其他模块；任一模块失败只在该模块内提示并可单独重试。

## 4. 功能需求

### FR-1 四模块定义与字段归属（P0）

- 系统必须按 §2.2 定义四个模块，并按 §2.3 完成字段归属；任一模块响应只包含本模块字段。
- 模块内现有字段的名称、类型、语义、条数上限、清洗规则保持不变（含 `scores` 恰好 5 项且维度名固定、`businesses` 2–4 项、上下游/合作各 ≤3 家、`rationale` 清洗规则等）。
- 前端按模块渲染，不得把其他模块字段作为本模块的必填依赖；缺失可选字段（如 `leaders`、`chain`、`partners`）时按现有空值规则隐藏。
- 模块四 `business_model` 在 R26 不实现、不渲染、不请求（见 FR-14）。

### FR-2 每个模块独立的「一键分析」（P0）

- 每个已上线模块卡片内必须有独立按钮（建议文案「一键分析」）。
- 点击某模块按钮时：
  - 只发起该模块的分析请求，**不得**同时触发其他模块；
  - 该模块进入 `loading`，按钮显示加载态并禁用；其他模块状态与结果不变；
  - 成功只更新该模块结果、token 用量与耗时；失败只在该模块内展示错误与重试入口。
- 模块按钮在未选择股票或股票代码非法时禁用/提示；与现有「未配置 apikey」错误提示口径一致。
- 模块的年份范围沿用现有页面级 `startYear`/`endYear`；未指定时仍按「最新年报 − 4」兜底（逻辑不变）。

### FR-3 顶部「一键全分析」（P0）

- AI 板块顶部（标题行或工具栏）必须有「一键全分析」按钮。
- 点击后必须**同时发起**全部已上线模块的分析（并发，不串行排队）；不得只做一次合并调用再由后端拆包（见 Q2）。
- 全分析的取数必须复用同一份上游数据：行情、三表、主营构成、增长快照、行业分类/同行榜在一次请求内各取一次，禁止每个模块各取一遍（该约束要求全分析由服务端统一处理，推荐 Q1 的方案 B；若选择方案 A 的前端并发多请求，需另行解决重复取数，否则不满足本 FR）。
- 全分析期间：
  - 全局按钮显示加载态并禁用；
  - 每个模块卡片展示各自的加载态；
  - 单个模块失败不得中断其他模块；成功后各自渲染。
- 全分析结束后，成功模块展示结果，失败模块展示错误与独立重试；至少一个模块成功时，请求整体按成功处理（见 FR-9 的响应语义）。
- 全分析必须与单模块共享缓存：某模块单点分析过且未过期时，全分析直接命中该模块缓存，不重复调用 LLM。

### FR-4 删除「分析模式」，固定详细档（P0）

- 必须删除请求参数 `reasoning`（`low/medium/high`）及其全部语义；服务端不再按模式选择篇幅。
- 所有模块一律按**详细档**生成：总体结论目标约 300 字（原 `high` 口径）；其他内容沿用各自既有固定篇幅约束（行业 1–2 句/项、业务板块 1 句前景 + 1 句风险、`rationale` ≤3 句等）。
- 删除 `aiConclusionSpec(reasoning)` 的分支逻辑，固定返回详细档要求；`BuildAIPrompt` 不再接收 `reasoning` 参数。
- 前端删除分析模式选择器、`aiReasoning` 状态、请求中的 `reasoning` 参数、提示文案中的模式说明。
- 若旧调用方仍传入 `reasoning`，服务端**忽略**该参数（不报错、不影响结果）；不得因参数出现而回退到旧语义。
- 对推理模型是否发送固定 `reasoning_effort` 由技术设计确定；若发送，建议固定为 `high` 以匹配详细档，且不得再由用户参数控制。当前默认模型 `deepseek-flash` 不发送该字段，行为不变。
- 明确不改变：五维评分标准、行业/业务板块/相关公司内容规则、估值参数确定性口径。

### FR-5 模块数据依赖与零新增数据源（P0）

- 单模块请求只取该模块所需数据（按 §2.4），不执行无关的确定性计算（如行业模块不执行六维指标计算）。
- 全分析在一次请求内完成并集取数，禁止重复取数；取数失败与降级规则沿用现状（如主营构成失败不阻塞、行业龙头失败降级为空并记日志）。
- 不新增东财/腾讯/其他数据源；不改变三表期数、年报过滤、年份兜底与代码校验。
- 模块级失败边界：三表/行情是财务与估值模块的硬依赖，失败则该模块失败；行业龙头/行业分类失败只降级不影响模块其余内容；主营构成失败按无主营构成处理。

### FR-6 后端接口形态（P0，关键决策见 Q1）

- 接口必须支持「单模块触发」与「全模块触发」两种能力，并满足：单模块只算该模块、全分析只取数一次、缓存按模块独立、未来新增模块不改既有模块。
- **推荐方案**：沿用 `GET /api/stock/:code/ai-analysis`，新增 `module` 参数，取值 `financial | industry | valuation | business_model | all`；缺省按 `all`（等价于原「一次返回全部」的语义）。
- 响应需提供模块级 `status`、模块结果、模块级 `usage` 与耗时；全分析返回各模块结果与合计用量（逻辑结构建议见 §5.4，具体字段命名由技术设计确定）。
- 不新增独立路由、不新增页面入口；R27 只需增加 `business_model` 枚举值与实现，不改动既有模块。
- 请求非法（代码非 6 位、`module` 非法、年份范围非法）按现有错误语义返回；单模块不存在时返回明确错误。

### FR-7 LLM 调用模型（P0，关键决策见 Q2）

- 每个模块独立发起一次 LLM 调用；单模块分析 = 1 次调用；全分析 = 已上线模块数（R26 为 3 次，R27 后为 4 次）**并发**调用。
- 禁止「一次 LLM 调用返回全部模块再由后端拆包」作为全分析实现（无法单模块触发，违背模块化诉求）。
- 每次调用沿用现有客户端参数：`temperature=0`、`response_format=json_object`、`max_tokens=8192`、超时 180s、429/5xx 自动重试；模块间重试互不影响。
- 各模块提示词只包含本模块所需事实（按 §2.4 裁剪），以控制输入 token；但不得因裁剪改变输出口径。
- 全分析并发上限不超过已上线模块数（R26 ≤3，R27 后 ≤4）；技术设计需考虑上游限流（现有客户端已对 429 退避重试），并保证一个模块重试不阻塞其他模块。
- 任一模块 LLM 失败只影响该模块；失败不写缓存，可单独重试。

### FR-8 模块级缓存与 schema 升级（P0）

- 缓存 key 必须新增模块维度并删除 `reasoning`：`{Schema, Code, Module, StartYear, EndYear, RangeSpecified}`（字段名由技术设计定）。
- `aiCacheSchema` 必须由 `"r25"` 升为 `"r26"`，使旧整包结果失效；不得尝试把旧整包缓存拆成模块缓存。
- TTL 保持 10 分钟；同模块同参数在途请求仍合并为一次计算；失败不缓存。
- 全分析对每个模块分别走「命中 → 复用；未命中 → 计算并写缓存」；单模块分析与全分析共享同一套模块缓存。
- 条目上限需按模块数复核：原 64 条在 3～4 模块下会更快触发淘汰，建议提升（如 128）或按模块独立计数，具体由技术设计确定，但不得因全分析一次写入 3～4 条而立即淘汰刚写入的其他模块结果。
- 前端本地缓存 key 同步改为 `代码|起始年|结束年|模块`（不再含模式）；全分析按模块分别写入本地缓存，便于后续单模块点击直接复用。

### FR-9 模块级状态、错误与部分失败（P0）

- 每个模块必须有独立状态：`idle / loading / ok / error / not_implemented`；前端按状态渲染空态、加载态、结果、错误与重试。
- 全分析中任一模块失败：其余模块正常展示；失败模块显示错误文案与「重试」按钮，重试只重试该模块。
- 响应语义建议：只要请求被正常处理（含部分模块失败），顶层 `code=0`，模块级 `status` 区分成功/失败；仅当全部请求模块均失败或请求本身非法时顶层 `code=1`。
- 错误文案不得泄漏提示词、内部字段名、阈值、schema 等过程信息；沿用现有错误风格。
- 某个模块结果缺失/字段异常时，只降级该模块（按现有解析容错规则），不得使其他模块失败。

### FR-10 估值自动套用仅由估值模块触发（P0）

- 现有行为「AI 结果落地后自动把推荐参数套用到估值表单并触发一次估值计算」必须保留，但**仅由估值模块结果触发**。
- 财务模块、行业模块成功返回时，不得修改估值表单、不得触发估值请求。
- 全分析中估值模块成功后触发一次套用；估值模块失败则不套用、不清空用户已填参数。
- 估值模块缓存命中时同样自动套用（与现状一致），并保持 `source=ai` 的估值记录语义（R16）。

### FR-11 前端布局与展示（P0）

- AI 板块顶部为工具栏：标题 + 「一键全分析」按钮 + 模块快捷导航（可选，P1）；下方按固定顺序展示四个模块卡片：公司财务分析 → 行业分析 → 估值参数分析 → 商业模式分析（R26 不渲染模块四，见 Q6）。
- 每个模块卡片包含：卡片标题、一句话说明、独立「一键分析」按钮、状态标识、结果区、错误/重试区。
- 模块结果区沿用现有渲染能力：
  - 财务模块：雷达图 + 五维评分条 + 总体结论；
  - 行业模块：行业分析（名称/前景/竞争格局/应用方向）+ 行业龙头（含本公司排名）+ 业务板块（含板块龙头/相关公司）+ 产业链上下游 + 合作公司 + 对应免责声明；
  - 估值模块：现有估值参数完整展示（模型、FCF、折现率、增长参数、关键校验、警告、rationale、详情折叠）；
  - 模块四：R27 实现。
- 推荐「分模块卡片纵向堆叠」而非单一无边界长面板；不使用 2×2 网格（行业模块内容高度远大于其他模块，网格会造成大量留白）。
- 雷达图仅存在于财务模块；模块隐藏/切换后重新显示时需正确 resize（沿用现有 `resizeRadarOnShow` 机制）。
- 桌面与移动端均不得出现横向滚动；移动端卡片单列、按钮可点、长文本换行正常。

### FR-12 切换股票、重复分析与并发点击（P1）

- 切换股票时：清空所有模块的结果、错误、loading、耗时与全局错误；本地缓存按 code 隔离，不得把上一支股票的结果渲染到新股票。
- 同一股票、同一年份范围重复点击某模块：若前端本地缓存已有该模块结果，直接复用、不重复请求；否则请求服务端（服务端缓存仍会兜底）。
- 改变年份范围后，模块缓存 key 变化，需重新分析。
- 同一模块在途时，该模块按钮禁用，不得重复发起；不同模块可并行分析；任一模块在途时「一键全分析」禁用，避免重复全量调用。
- 页面刷新或重新进入股票后，允许依赖服务端缓存快速返回；前端不要求持久化模块结果。

### FR-13 Token 用量与耗时展示（P1）

- 每个模块结果区展示本模块本次调用的 token 用量与耗时（缓存命中时耗时可标注「缓存」或不展示，沿用现状）。
- 全分析额外展示合计 token 与总耗时（总耗时 ≈ 最慢模块耗时，不是各模块之和）。
- 不新增后端统计字段，沿用现有 `usage{prompt_tokens, completion_tokens, total_tokens}`；全分析合计为各模块求和。

### FR-14 模块四（商业模式）占位与 R27 扩展契约（P1）

- R26 不实现 `business_model` 的内容、提示词、解析与评分；前端默认**不渲染**该模块卡片（避免死按钮，见 Q6）。
- 接口对 `module=business_model` 必须返回明确「尚未上线」错误（或在全分析中以 `status=not_implemented` 跳过），不得返回空成功误导前端。
- 前端模块列表应由配置/注册表驱动（key、标题、说明、顺序、可用性），R27 上线时只新增一项即可出现卡片与按钮。
- R27 落地时：新增模块的字段、提示词、解析、缓存均独立；不得修改财务/行业/估值模块的提示词与输出口径；缓存 schema 升 `r27`。
- 模块四的位置固定在估值模块之后。

### FR-15 输出洁净与内容不变约束（P0）

- 各模块输出不得出现提示词、规则名、内部字段名、阈值、权重、schema、模块 key 等过程话术；沿用现有清洗规则（如 `rationale` 禁止数字与过程词）。
- 各模块不得编造财务数据；AI 推断内容（行业、业务板块、相关公司）保留现有「AI 推断/供参考」标注与免责声明。
- 五维评分：名称、顺序、0-100 范围、恰好 5 项、缺失报错的严格校验不变。
- 估值模块：模型选择、基期 FCF、WACC、增长参数、关键校验、警告与 `rationale` 清洗的确定性口径完全不变；AI 返回的模型/参数仍一律丢弃并由后端覆盖。
- 行业模块：行业/业务板块/相关公司的内容规则、条数上限、去重与排除自身规则不变（R17/D8/D10）。

## 5. 接口与调用模型方案（关键决策）

### 5.1 接口形态：A/B/C 对比与推荐（对应 Q1）

| 方案 | 形态 | 优点 | 缺点 |
|---|---|---|---|
| A | 4 个独立端点（`/ai-analysis/financial`、`/industry`、`/valuation`、`/business-model`） | 语义直观；每个端点可只取所需数据；独立限流/监控 | 路由与 handler 数量增加；全分析需要前端并发 4 个请求，后端无法共享一次取数，导致 4 倍上游请求；响应聚合与错误处理分散 |
| B | 1 个端点 + `module` 参数（`financial/industry/valuation/business_model/all`） | 单路由易维护；`all` 可在后端一次取数、并发调用；缓存按模块自然分裂；新增模块只加枚举值；前端 URL 统一 | 需要定义模块级响应包装；单端点内分支较多 |
| C | 1 个端点 + `modules` 多选参数 | 表达力最强，可选择任意模块子集 | 前端无「任意子集」诉求；响应聚合、缓存与错误语义更复杂；收益低于复杂度 |

**推荐：方案 B**。理由：

1. **取数效率**：`module=all` 在后端一次取数后并发分析，避免前端并发多请求造成重复取数（东财/腾讯接口对频率敏感）。
2. **缓存一致**：单模块与全分析共用同一套「模块 key」缓存；方案 A 若前端并发 4 请求，仍可共享服务端缓存，但取数重复问题无法在 handler 内解决。
3. **可扩展**：R27 只需新增 `business_model` 枚举与模块实现；不必新增路由或改前端请求封装。
4. **兼容**：缺省 `module=all` 保留「一次拿到全部」的旧语义；旧 `reasoning` 参数直接忽略。
5. **前端简单**：一个请求构造函数，按按钮传入不同 `module`。

### 5.2 LLM 调用模型：独立调用 vs 合并调用（对应 Q2）

| 方案 | 形态 | 优点 | 缺点 |
|---|---|---|---|
| 每模块独立调用 | 单模块 1 次；全分析 N 次并发 | 天然模块化；可单模块触发/重试/缓存；每个提示词更聚焦；单次输出压力从「全部板块」降为「一个板块」，截断风险下降 | 输入 token 重复（基础事实块按模块各发一次）；全分析瞬时并发 N 个请求；模块间上下文不再共享 |
| 合并一次调用后拆包 | 1 次返回全部，后端拆分 | token 成本最低；上下文天然一致 | 无法单独触发某模块（单模块也要跑全部）；与「同时发起分析」的模块化诉求冲突；无法按模块缓存与重试 |

**推荐：每模块独立调用；「一键全分析」= 各模块并发独立调用（R26 3 次，R27 后 4 次）**。理由：

1. 模块化本质要求「单独触发、单独缓存、单独失败重试」，合并调用无法满足。
2. 单模块分析可显著降低等待与 token（只发本模块事实、只产出本模块内容）。
3. 单次输出上限 8192 token 从「全部板块共享」变为「每模块独享」，R27 九要素等长内容更安全。
4. 全分析总耗时约等于最慢模块，而非各模块之和；并发上限仅 3～4，低于现有客户端重试能力与常规限流阈值。
5. 输入 token 重复可通过 §2.4 的按模块裁剪抵消一部分；成本增加是可接受、可度量的代价。

**一致性影响（必须明确接受或缓解）**：

- 拆分前，总体结论、行业分析、业务板块、估值 rationale 在同一次上下文内生成，彼此天然一致。
- 拆分后，各模块独立生成，**不保证**逐句互相呼应；可能出现的差异示例：财务结论对行业前景的描述与行业模块措辞不同；估值模块的 `industry_type` 与行业模块的行业描述口径不完全一致。
- 缓解措施（本需求内）：
  - 各模块使用同一份后端事实与同一模型、`temperature=0`；
  - 行业模块的行业名称优先采用后端确定性行业分类（与龙头榜一致）；
  - 估值模块的 `industry_type` 仍只作为估值分类，不向行业模块传播；
  - 每个模块内部不得自相矛盾（如评级与文字冲突）。
- **明确接受**：R26 不做跨模块一致性校验或二次对齐；跨模块差异属于模块化设计的已知代价。若必须一致，可在后续需求增加「一致性复核」步骤或共享中间结论。见 Q10。

### 5.3 推荐响应逻辑结构（命名由技术设计确定）

单模块：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "module": "financial",
    "status": "ok",
    "message": "",
    "result": { "scores": [], "conclusion": "" },
    "usage": { "prompt_tokens": 0, "completion_tokens": 0, "total_tokens": 0 },
    "elapsed_ms": 0,
    "cached": false
  }
}
```

全分析：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "modules": {
      "financial": { "status": "ok", "result": {}, "usage": {}, "elapsed_ms": 0, "cached": false },
      "industry": { "status": "ok", "result": {}, "usage": {}, "elapsed_ms": 0, "cached": true },
      "valuation": { "status": "error", "message": "分析失败，请重试", "result": null },
      "business_model": { "status": "not_implemented", "message": "将于 R27 上线" }
    },
    "usage": { "prompt_tokens": 0, "completion_tokens": 0, "total_tokens": 0 },
    "elapsed_ms": 0
  }
}
```

- 全分析 `usage` 为各成功模块之和；`elapsed_ms` 为请求总耗时。
- `result` 内字段严格按 §2.3，不得混入其他模块字段。
- 若技术设计采用不同字段名，必须保持「模块级状态 + 结果 + 用量独立、全分析可聚合、部分失败可渲染」四项能力。

## 6. 缓存与 schema

### 6.1 缓存 key 与容量

- key 维度：`Schema + Code + Module + StartYear + EndYear + RangeSpecified`；删除 `Reasoning`。
- `RangeSpecified` 语义保留：区分「未指定年份（计算时兜底为最新年报 − 4）」与「显式指定 0/0（非法年份）」。
- TTL 10 分钟不变；同 key 在途合并机制保留。
- 条目上限：原 64 条按「整包结果」设计；模块化后一次全分析会写入 3～4 条，建议提升至 128 或按模块分别计数，避免频繁整体清空。具体值由技术设计确定，验收要求「连续分析 ≥8 只股票且各模块结果仍可命中」。

### 6.2 全分析的命中与回填

- 全分析请求进入后，对每个模块独立调用 `getOrCompute`：
  - 命中：直接返回缓存结果，`cached=true`，不调用 LLM；
  - 未命中且在途：复用同模块在途请求；
  - 未命中且空闲：发起该模块 LLM 调用，成功后写该模块缓存。
- 任一模块失败不写缓存，也不影响其他模块写入。
- 单模块请求与全分析请求共享同一缓存实例与同一 key 规则。

### 6.3 前端本地缓存

- key 改为 `代码|起始年|结束年|模块`；不再含分析模式。
- 全分析返回后按模块分别写入本地缓存；后续单模块点击命中本地缓存时直接渲染（并触发估值模块的自动套用，若命中估值模块）。
- 切换股票时不清空整个本地缓存（按 code 隔离即可），但必须清空当前股票的结果展示状态。

### 6.4 schema 升级顺序

- R26：`r25 → r26`。原因：结果由整包变为模块级、删除 `reasoning`、新增模块 key 维度。
- R27：`r26 → r27`。原因：新增 `business_model` 模块与字段。
- 不提供旧缓存迁移；旧缓存因 schema 不同自然失效。
- 若 R26 与 R27 合并为一次发布，可一次性升级到 `r27`；当前既定顺序为先后开发，采用顺序升级。

以下内容**不得改变**（只允许移动位置与复用渲染，不允许改算法、提示词规则或字段语义）：

1. **五维评分**：维度名与顺序（盈利能力、偿债能力、现金获取能力、经营效率、成长能力）、0-100 整数、恰好 5 项、缺失报错、评分标准与行业适配说明。

## 12. 待确认问题

> 每项给出推荐默认值；未确认前按推荐值进入技术设计。Q1、Q2 为影响最大的两项关键决策。

### Q1 后端接口形态：独立端点（A）/ 单端点 + module（B）/ 单端点 + modules 多选（C）？

- **影响**：直接决定取数次数、缓存结构、前端请求封装、R27 扩展成本与错误语义。
- **推荐**：**方案 B——单端点 + `module=financial|industry|valuation|business_model|all`，缺省 `all`**。理由：全分析可在后端一次取数并发调用，避免 3～4 倍上游请求；单模块与全分析共享模块缓存；R27 只加枚举值；前端只维护一个请求构造函数。详见 §5.1。
- **备选**：A 语义最直观，但全分析会重复取数；C 表达力强但无实际诉求且聚合复杂。

### Q2 LLM 调用模型：每模块独立调用（全分析并发 N 次），还是合并一次调用后拆包？

- **影响**：决定能否真正单模块触发、token 成本与延迟、模块间一致性。
- **推荐**：**每模块独立调用；全分析 = 已上线模块并发独立调用**（R26 3 次，R27 后 4 次）。理由：模块化的必要条件；单模块省时省 token；单次输出上限独享、截断风险下降；全分析耗时约等于最慢模块。代价是输入 token 重复与模块间不再共享上下文，已通过按模块裁剪输入、同模型 `temperature=0`、确定性字段后端统一来缓解；**明确接受模块间措辞不完全一致**（见 §5.2、Q10）。
- **备选**：合并一次调用后拆包，成本最低但与「单独分析某模块」根本冲突，不推荐。

### Q3 「总体结论」拆分到财务模块后的口径：纯财务，还是保留跨模块呼应？

- **影响**：影响结论内容与用户对「财务模块是否该谈商业模式/估值」的预期；R27 落地后可能与商业模式模块重复。
- **推荐**：**R26 保持现有 5 段式不变**（以财务为主，保留「公司质地与商业模式」「护城河」的轻量定性呼应，不引用估值数值）。理由：本需求硬约束是「输出内容保持相同」，改写结论会直接破坏 AC-19 的内容等价；且 R26 尚未有商业模式模块，财务结论中的轻量商业模式描述仍是唯一入口。**R27 落地后再评估**是否把商业模式部分收窄为一句呼应或交由模块四承载（可作为 R27 的修订项）。
- **备选**：R26 即改为纯财务结论（删除商业模式/护城河段落）。会让财务模块更聚焦，但与「内容不变」冲突，需用户明确同意后才可执行。

### Q4 全分析的结果呈现：整体返回，还是逐模块渐进返回？

- **影响**：整体返回实现简单、只取数一次；渐进返回体验更好，但需要 SSE 或前端并发多请求（导致重复取数）。
- **推荐**：**R26 采用单请求 `module=all`、后端并发、整体返回**；各模块卡片先显示 loading，全部完成后一起渲染。理由：与 Q1/Q2 的取数复用一致，不引入流式协议；「同时发起」的诉求已满足。
- **备选**：前端并发 3 个单模块请求以渐进展示。体验更好，但上游取数重复 3 倍，且与后端一次取数的设计冲突；可作为后续增强（需服务端增加取数缓存或 SSE）。

### Q5 前端结果布局：分模块独立卡片，还是单一长面板按节分区？

- **影响**：影响可读性、移动端体验与后续模块扩展。
- **推荐**：**分模块独立卡片纵向堆叠**（财务 → 行业 → 估值 → 商业模式），每卡片自带标题、按钮与状态；不做 2×2 网格。理由：行业模块内容高度远大于其他模块，网格会大量留白；独立卡片让「单模块分析」在视觉上自洽；后续加模块只需追加一张卡片。
- **备选**：单一长面板按节分区（现状风格）。改动小，但模块边界弱，单模块分析后会出现大段空白/不完整感。

### Q6 R26 是否展示「商业模式分析」占位卡片？

- **影响**：占位可提前暴露模块化结构，但会留下不可用按钮；不展示则界面干净，但用户看不到第四个模块的规划。
- **推荐**：**R26 不渲染模块四**（避免死按钮与误导）；前端模块列表配置化，R27 上线时直接新增一项。理由：R26 的验收范围是三个可用模块；占位按钮无实际价值，且容易让用户反复点击。
- **备选**：展示置灰卡片并标注「R27 上线」。适合希望界面提前体现完整框架的场景，但需接受不可用控件。

### Q7 缓存条目上限如何调整？

- **影响**：原 64 条按整包结果设计；模块化后一次全分析写入 3～4 条，过早淘汰会降低命中率、增加 token 消耗。
- **推荐**：**提升到 128 条**（约 32 组「股票 + 年份」× 4 模块），或按模块独立计数；TTL 保持 10 分钟。具体值由技术设计结合内存占用确定。
- **备选**：维持 64 条并接受更频繁的整体清空。内存更省，但全分析场景命中率明显下降。

### Q8 是否兼容旧客户端（旧 `reasoning` 参数、旧整包响应）？

- **影响**：兼容层会保留旧语义与旧结构，增加维护成本并阻碍模块化。
- **推荐**：**不做兼容层**：删除 `reasoning` 语义（传入则忽略）、升级 schema 使旧缓存失效、前后端同版本发布。理由：单仓内嵌单前端，无外部调用方；兼容层收益极低。
- **备选**：保留 `module` 缺省整包旧结构 + 新模块参数并存。会让接口出现两套响应形态，不推荐。

### Q9 行业模块的输入是否可裁剪为「主营构成 + 行业分类 + 同行榜」？

- **影响**：裁剪可显著降低输入 token；若裁剪过度，可能影响行业前景/业务板块判断质量。
- **推荐**：**允许裁剪**，但需以「拆分前后行业模块输出结构、条数与字段约束一致」验证；若发现质量下降，保留最近一年营收/毛利率/ROE 等少量关键指标作为补充。具体由技术设计确定。
- **备选**：所有模块继续发送完整六维指标序列。质量最稳，但输入 token 最贵且与单模块省成本的初衷冲突。

### Q10 模块间一致性：接受各自独立，还是增加跨模块复核？

- **影响**：独立生成可能造成财务结论、行业描述、估值分类的措辞或判断不完全一致；跨模块复核可提升一致性，但需要额外调用/规则与成本。
- **推荐**：**R26 接受各模块独立**，仅保证模块内部自洽与确定性字段后端统一；不增加复核调用。理由：模块化的核心价值是独立触发与独立缓存；跨模块一致性不是本需求的目标，且现有 `temperature=0` + 同一事实源已能降低大部分差异。
- **备选**：全分析完成后增加一次轻量一致性检查（或把行业/估值结论回灌给财务结论）。会增加一次调用与缓存复杂度，建议另立需求。
