## 1. 背景与目标

### 1.1 背景

- 用户会在不同时间、用不同假设（模型、折现率、增长率、基期 FCF 选取方式）对多只股票计算估值，但页面是**单股上下文**：一旦搜索下一只股票，上一只的估值结果即被覆盖，**无任何地方可以回看**。
- 现有 `fetchValuation()` 只在内存中保存当前结果（`valuation` ref），刷新页面或切换股票即丢失；用户需要凭记忆重新输入参数、重新计算。
- 顶部搜索历史（`stockSearchHistory`）只记录「看过哪些股票」，不含任何估值参数与结果，无法承担「估值记录」的职责。
- 用户明确要求：① 自动记录；② 能在页面上查看公司及其估值；③ 可手动清除。并点名要设计**放置位置**。
- 首版把记录存在浏览器 localStorage，存在两个痛点：
  1. **按 origin 隔离**：换浏览器、清浏览器数据、换服务端口或域名就看不到旧记录；
  2. **无法跨设备**：同一服务跑在另一台电脑/另一个人用不同浏览器访问时，各看各的记录，不能共享同一份估值结论。
- 项目定位仍是单用户、单二进制、无数据库的轻量工具；记录数据结构固定、条数上限 50、单文件约 30–50 KB，**用 JSON 文件持久化即可**，无需引入数据库。

### 1.2 目标

- 用户主动计算过估值的公司，自动形成一条**服务端持久化**的记录：同一服务端地址下，换浏览器、换设备、刷新页面、重启服务后仍可查看同一份列表。
- 打开记录可快速回到该公司的分析页，并按记录中的模型与参数重新计算，省去重复录入。
- 记录的管理成本要低：单条删除、一键清空，清空有二次确认；所有写操作在服务端完成去重、排序与 50 条截断。
- 页面其余功能与现有卡片布局保持不变；后端新增轻量文件存储与 4 个读写接口，估值、指标、AI 等既有接口契约不变。
- 升级不丢用户已有数据：浏览器中已有的旧记录应尽量迁移到服务端（见 FR-15）。

## 2. 用户故事 / 使用场景

- 作为个人投资者，我想要把算过的几只公司估值自动留存下来，下次打开页面就能回看「当时用的模型、参数和算出的每股价值」，以便比较和复盘。
- 作为正在查看某只股票的投资者，我想要在估值卡片算完后立刻知道「这次已记录」，并且随时从顶部打开记录列表，以便确认记录是否成功。
- 作为反复试参数的投资者，我想要点一条旧记录就能恢复当时的参数并重算，以便在旧假设上继续调整，而不必手工重填所有输入框。
- 作为只需要最近结论的用户，我想要删除某一条或清空全部记录，以便让列表保持干净。

## 3. 功能需求

### FR-1 记录触发：只记录「用户主动发起」的成功估值（P0）

**定义：一条估值记录 = 一次由用户主动发起、且成功返回结果的估值计算。**

| 动作 | 是否记录 | 记录来源标记 |
| --- | --- | --- |
| 用户在「公司估值」卡片点击「计算估值」并成功返回 | **记录** | `manual`（手动计算） |
| 用户在 AI 分析中点击「套用到估值」，回填参数并计算成功 | **记录** | `ai`（AI 推荐） |
| 搜索/切换股票时 `doSearch()` 自动触发的估值计算 | **不记录** | — |
| 点击历史记录回填参数后的重新计算 | **不记录** | — |
| 参数本地校验失败、HTTP 失败、返回 `code != 0`、响应解析失败 | **不记录** | — |

- **触发时机**：请求成功且结果已写入页面估值卡片后写记录；失败不得写入，也不得修改已有记录。
- **必须在请求发起时捕获股票代码与名称**（名称来自当前已加载的 `data.stock.name`，缺失时回退到搜索历史中的同名代码，再缺失显示「—」），用于识别记录归属；若响应返回时已切换到其他股票，按 FR-12 丢弃该响应，**不写卡片、不写记录**。
- **理由（为何排除自动计算）**：`doSearch()` 对每只被搜索的股票都会自动算一次估值；若一并记录，记录列表会退化成「搜索历史」，违背「计算过估值」的语义。
- **AI 套用为何记录**：它是用户主动点击、且会改变估值卡片结果的动作，与手动计算同为「一次确定的估值决策」，应可回看；来源标记用于在列表中区分。

### FR-2 记录内容：保存本次计算的结果快照（P0）

每条记录保存以下字段（字段名仅用于描述数据结构，技术实现可调整命名）：

| 字段 | 类型 | 取值来源 | 说明 |
| --- | --- | --- | --- |
| `code` | string | 请求路径中的 6 位代码 | 记录主键（同一代码只保留一条，见 FR-3） |
| `name` | string | `data.stock.name` → 搜索历史 → 空串 | 公司名称 |
| `market` | string | `guessMarket(code)` | `sh`/`sz`/`bj`，用于市场徽标 |
| `createdAt` | string | **服务端写入时刻**，ISO 8601（UTC） | 记录时间（每次覆盖更新时刷新）；客户端传入值忽略，见 FR-13 |
| `source` | string | `manual` / `ai` | 记录来源 |
| `year` | int | `valuation.year` | 基期年报年份 |
| `model` | string | `valuation.model` | 模型 key |
| `modelName` | string | `valuation.model_name` | 模型中文名 |
| `discountRate` | number | `valuation.discount_rate` | 折现率 % |
| `growthRate` | number? | `valuation.growth_rate` | 永续增长率 %（perpetual） |
| `stage1Growth` / `stage1Years` | number? / int? | 对应字段 | 两/三阶段第一阶段 |
| `stage2Growth` / `stage2Years` | number? / int? | 对应字段 | 两/三阶段第二阶段 |
| `terminalGrowth` | number? | `valuation.terminal_growth` | 三阶段终值增长率 % |
| `fcfMode` / `fcfModeName` | string | 对应字段 | 基期 FCF 选取方式 key / 中文名 |
| `fcfYears` | int? | `valuation.fcf_years` | 选取年数（平均值/中位数/去极值） |
| `adjustRD` | bool | `valuation.adjust_rd` | 是否研发调整 |
| `rdAdjustment` | number? | `valuation.rd_adjustment` | 研发扩张加回金额（元） |
| `fcfCustomValue` / `fcfCustomUnit` | number? / string? | 对应字段 | 仅自定义模式 |
| `baseFCF` | number | `valuation.base_fcf` | 基期经营资产自由现金流（元） |
| `financialAssetValue` | number | 对应字段 | 金融资产价值（元） |
| `longEquityValue` | number | 对应字段 | 长期股权投资价值（元） |
| `operatingAssetValue` | number | 对应字段 | 经营资产价值（DCF，元） |
| `companyValue` | number | 对应字段 | 公司价值（元） |
| `debtValue` | number | 对应字段 | 债务价值（元） |
| `equityValue` | number | 对应字段 | 股权价值（元） |
| `equityValuePerShare` | number | 对应字段 | 每股股权价值（元）；总股本缺失时为 0/缺省 |

- 记录是**计算时点的结果快照**：后续年报数据、股价、总股本变化都**不得**自动改写已有记录。
- 不保存 `notes` 提示、AI 结论、行情价格等非估值结果字段（控制体积，避免超出「估值记录」语义）。
- 展示用的「参数摘要」不单独存储，由上述字段现算（格式见 FR-6）。

### FR-3 去重、排序与条数上限（P0）

- **同一公司只保留一条**：以 `code` 为唯一键。再次计算同一公司时，用新结果**整体覆盖**旧记录，`createdAt` 刷新为本次时间，并移动到列表首位。
  - 理由：用户诉求是「记录计算过估值的公司，查看对应的估值」，以公司为粒度最直观；若每次计算都追加，反复调参会迅速淹没列表，也无法一眼看出「这家公司现在是什么结论」。
  - 覆盖即意味着**不保留同一公司的历史版本**（已知取舍，见第 8 节 Q2）。
- **排序**：列表固定按 `createdAt` 倒序（最近计算的在最上面），不提供用户排序。
- **上限**：最多保留 **50 条**（`MAX_VALUATION_RECORDS = 50`）。新增公司导致超限时，淘汰 `createdAt` 最早的一条；覆盖更新已有公司不触发淘汰。
- **执行位置**：去重、置顶、时间刷新、排序与 50 条截断**全部由服务端在写入时执行**（FR-13）；前端不再自行去重/截断，只按接口返回的列表展示，打开抽屉时以服务端列表为准。
- 记录为空时，顶栏入口的计数徽标不显示数字。

### FR-4 存储与持久化：后端 JSON 文件（P0，本版重写）

#### FR-4.1 文件格式

- 单个 JSON 文件，沿用现有带版本的信封结构，**字段名与 FR-2 完全一致（camelCase）**：

```json
{
  "version": 1,
  "items": [ { "code": "600519", "name": "贵州茅台", "...": "..." } ]
}
```

- 金额字段一律为**元**；不适用字段存 `null`（不是省略），保证文件结构稳定、可直接人工查看。
- `version` 固定为 `1`（与现有 localStorage 信封一致），便于未来迁移；读取时 `version != 1` 或 `items` 非数组 → 视为空列表。
- 文件内容始终按 `createdAt` 倒序、`code` 唯一、最多 50 条保存；服务端写入时保证该不变量（读取到不合规的旧文件时，在内存中归一化，下一次写入时落盘修正）。`createdAt` 相同的极端情况按写入顺序、后写入者在前，保证排序确定。

#### FR-4.2 文件位置（推荐默认值）

- 启动参数新增 `-data <目录>`：数据目录，缺省 `./data`（相对**进程工作目录**）。
- 记录文件固定为 `<data>/valuation_history.json`。
- 理由：项目是单二进制、无数据库的个人工具，通常从项目根目录 `go run ./cmd/server` 启动；放在工作目录下的 `data/` 中**可见、易备份、易删除**，不引入跨平台用户目录解析。换工作目录启动会指向另一份数据，需用 `-data` 显式指定（已知限制）。
- 备选（不推荐）：`os.UserConfigDir()`（macOS 为 `~/Library/Application Support/...`），不受工作目录影响但路径不直观、跨平台不一致。
- 启动时尝试 `MkdirAll(<data>, 0755)`：创建失败只记录日志并继续提供服务（估值等既有功能不受影响），记录读写接口返回错误（见 FR-13.5）。
- `.gitignore` 增加 `/data/`，避免把个人估值记录提交进仓库。

#### FR-4.3 读写与原子性

- 服务端以一个**互斥锁串行**所有读改写：每次请求在锁内完成「读文件 → 校验/归一化 → 变更 → 原子写回」，不维护长期内存副本（文件 ≤50 KB，读取成本可忽略）。
- **原子写入**：先写同目录临时文件（如 `valuation_history.json.tmp-<随机后缀>`）→ `Sync` → `os.Rename` 覆盖目标文件。进程在写入中途退出时，旧文件保持完整，不产生半截 JSON。目标平台以 macOS/Linux 为准（`os.Rename` 覆盖已存在文件的原子语义）；Windows 不是本期验收目标。
- **读取容错**：
  - 文件不存在 → 空列表，HTTP 成功，不报错。
  - 读取失败或 JSON 解析失败 → 视为空列表并记录 warning 日志；可将损坏文件重命名为 `valuation_history.json.corrupt-<时间戳>` 留档（P1，避免下一次写入静默覆盖可恢复数据）。
  - 单条字段类型非法 → 丢弃该条；`code` 非 6 位数字或 `createdAt` 非法的条目直接丢弃；重复 `code` 保留 `createdAt` 最新的一条。
- **写入失败**（磁盘满、目录只读等）：**不得**改动内存/磁盘中的既有列表；接口返回 `code=1` 与可读错误信息（FR-13.4），前端据此提示用户。
- 不做文件级跨进程锁（见第 5 节多实例边界）。

#### FR-4.4 localStorage 的角色（本版收窄）

- 新记录**不再写入** localStorage；`valuationHistory` 键仅作为**旧数据迁移来源**保留（FR-15），迁移完成后不自动删除，作为一次性备份。
- 「首次记录提示」的本地标记 `valuationHistoryHintShown` 仍保留在 localStorage（纯粹是每浏览器的 UI 提示状态，不属于记录数据）。
- 搜索历史 `stockSearchHistory` 与本次改造无关，仍为 localStorage（见第 5 节）。

### FR-5 顶栏入口与抽屉（P0）

- 在**顶栏**新增常驻入口「估值记录」，位于搜索区域右侧（桌面端），展示时钟/列表图标 + 文字 + 数量徽标（数量为 0 时不显示徽标）。
  - 入口在**欢迎页与结果页均可见**（记录是全局数据，不属于某只股票）。
  - 点击打开右侧抽屉 `el-drawer`，标题「估值记录」，标题右侧提供「清空全部」文字按钮。
  - 桌面端抽屉宽度约 420px；视口 ≤768px 时抽屉占满屏幕宽度。抽屉打开时页面其余内容不跳动。
- **入口不能挤占搜索框**：移动端（≤768px）搜索栏独占一行，入口留在品牌行右侧；≤480px 时入口只显示图标与徽标（`aria-label="估值记录"` 保证可读）。
- 入口用按钮语义实现（`<button>`），支持键盘 Tab 聚焦与 Enter 打开；沿用现有 `.clear-hist-btn` 的浅色描边风格，保持顶栏视觉一致。
- **打开抽屉时刷新**：每次打开抽屉都发起一次 `GET /api/valuation-history`（FR-13），以服务端列表覆盖本地内存并回到第 1 页；这样在其他浏览器/设备新增或删除的记录能在本次打开时看到。刷新期间展示加载态；失败处理见 FR-14。

### FR-6 记录列表展示（P0）

- 列表形态为**卡片式条目**（非表格），每条三行，信息层级如下：

| 行 | 内容 |
| --- | --- |
| 第 1 行 | 公司名称（加粗）+ 6 位代码 + 市场徽标；右侧：来源标签（仅 `source=ai` 显示「AI 推荐」）+ 删除图标按钮 |
| 第 2 行 | **每股股权价值 X.XX 元**（主结果，加粗）；次列「股权价值 X.XX亿」；每股值缺失时改为突出「股权价值」 |
| 第 3 行（弱化小字） | 模型中文名 · 折现率 X% · 基期 FCF {方式}{（N年）} · 基期 {year} 年报 · 记录于 {YYYY-MM-DD HH:mm}；`adjustRD=true` 时追加「· 研发调整」 |

- **参数摘要格式**（固定顺序）：`{modelName} · 折现率 {discountRate}% · 基期FCF {fcfModeName}{（{fcfYears}年）} · 基期 {year} 年报`；自定义模式显示 `基期FCF 自定义 {fcfCustomValue}{单位}`（单位沿用页面的 亿/万/千/元 标签）。
- **数值格式**：
  - 每股股权价值保留 2 位小数并加「元」；无法计算（总股本缺失）显示「—」。
  - 金额用现有 `fmtYi` 口径（≥0.01 亿显示「X.XX亿」，否则「X.XX万」）。
  - 折现率/增长率用现有 `fmtNum` 口径（整数不带小数，其余 2 位）。
  - 时间显示为本地时间的 `YYYY-MM-DD HH:mm`，不使用相对时间（避免歧义）。
- **交互**：整条可点击（鼠标悬停高亮 + 指针），点击行为见 FR-7；删除按钮点击必须阻止冒泡，不能触发整条跳转。
- 抽屉顶部显示记录条数（如「估值记录 3」）。
- 抽屉底部固定一行弱化说明：「记录为计算时的快照，点击后将按当时参数重新计算。」
- **分页**（沿用现状）：列表每页 10 条，底部 `el-pagination`；打开抽屉回到第 1 页。删除/刷新后若当前页超出总页数，自动回退到最后一页；无记录时不显示分页。
- **加载与失败态**：
  - 首次打开或刷新中且列表为空 → 展示加载占位（骨架/`v-loading`），不闪空态文案。
  - 刷新失败且本地已有上次加载的列表 → 保留列表，并在列表上方显示一行弱化警告「刷新失败，显示的是上次加载的记录」+「重试」按钮。
  - 刷新失败且列表为空 → 空态区域展示「暂时无法加载估值记录」+「重试」按钮，不误报「还没有估值记录」。
  - 加载/失败状态不得影响估值计算与页面其他卡片。

### FR-7 点击记录：回填参数并重新计算（P0）

- 点击某条记录（删除按钮除外）时：
  1. 关闭抽屉；
  2. 将顶部搜索框设为该记录的 6 位代码，按现有搜索流程加载该股票（等价于 `doSearch()`，会一并刷新指标、报表、六维分析、公司价值、AI 分析区）；若与当前股票不同，**先按 FR-12 将估值卡片重置为默认**；
  3. **在重置之后**将记录中的估值参数回填到「公司估值」表单：模型、折现率、各阶段增长率与年数、基期 FCF 模式/年数/自定义值与单位、研发调整开关（覆盖默认值）；
  4. 基于回填后的参数自动重新计算估值并展示。
- **时序要求**：「重置 → 回填 → 自动计算」顺序不可颠倒；回填须发生在搜索流程发起估值请求之前，确保自动计算使用的是记录参数而非默认参数。
- 若该记录就是当前正在查看的股票：不发生换股，不触发 FR-12 重置，直接回填参数并重算，不新增记录。
- **不得修改被点击的记录**：不刷新 `createdAt`、不覆盖快照值。若因数据更新导致重算结果与快照不同，页面展示最新计算值，抽屉中仍保留历史快照（两者并存，属预期）。
- 重算失败（如当前数据不满足模型条件）时，沿用估值卡片现有的错误提示；记录本身不受影响。

### FR-8 单条删除（P0）

- 每条记录右侧提供删除图标按钮（垃圾桶），点击后删除该条记录，无需二次确认（代价低、可重新计算恢复）。
- 删除由服务端执行（`DELETE /api/valuation-history/:code`），前端以后端返回的列表为准：
  - 成功：列表减少一条、顶栏徽标计数同步、若删除的是最后一条则展示空态；给出轻量提示「已删除 XX 的估值记录」。
  - 失败（网络/服务端写失败）：**保留该条记录**并提示「删除失败，请重试」；不得出现「界面上删掉了但服务端还在」的假成功。
- 删除请求在途时，该条删除按钮置为 loading/禁用，避免重复提交。
- 单条删除**不影响**顶部搜索历史（`stockSearchHistory`）与当前页面正在展示的估值结果。

### FR-9 清空全部（P0）

- 抽屉标题栏右侧提供「清空全部」按钮；无记录时按钮禁用或隐藏。
- 点击必须弹出二次确认（`ElMessageBox.confirm`），文案包含条数：
  - 标题：「清空估值记录」
  - 内容：「确定清空全部 N 条估值记录？此操作不可恢复。」
  - 按钮：「取消」/「清空」（危险色）。
- 确认后调用 `DELETE /api/valuation-history`，成功后清空列表并展示空态；取消不做任何修改。
- 清空失败：保留列表并提示「清空失败，请重试」；不得只清前端。
- 请求在途时按钮置为 loading/禁用。
- 清空操作仅作用于估值记录，**不得**清空搜索历史、AI 缓存或页面当前估值结果；也不得删除 localStorage 中的旧数据备份（FR-15）。

### FR-10 空态与首次记录提示（P1）

- 抽屉无记录且最近一次加载成功时展示空态：图标 + 「还没有估值记录」+ 引导文案「在「公司估值」卡片点击「计算估值」后会自动记录在这里。」（AI 套用同样会产生记录，可在文案中不展开）。
- 产生**本浏览器第一条**估值记录时，展示一次轻提示：「已记录本次估值，可在顶部「估值记录」查看」，并用本地标记 `valuationHistoryHintShown` 确保只提示一次；之后依靠顶栏徽标数量变化提供反馈，不再逐次弹提示。该标记是纯 UI 状态，不随服务端记录迁移/清空重置。
- 记录保存失败时**必须**给出反馈（与旧 localStorage 静默降级不同）：估值结果照常展示，但提示「估值已计算，但记录保存失败：<原因>」，并**不**把该条加入列表；用户可重新点击「计算估值」重试。

### FR-11 记录与实时数据的边界（P0）

- 记录是**历史快照**，不随行情、年报更新自动刷新；列表不展示实时股价，也不计算「估值 vs 现价」的涨跌幅（避免暗示实时对比）。
- 每次用户主动「计算估值」或 AI「套用到估值」都会产生一次新的快照（同公司覆盖）。
- 仅查看记录（FR-7）产生的自动重算**不写入**记录。

### FR-12 切换股票时重置「公司估值」卡片（P0，2026-10-17 用户新增）

**目标：上一家公司的估值结果与参数对下一家公司没有意义，切换股票后不得残留。**

#### FR-12.1 触发点

- 当 `doSearch()` 解析出最终 6 位代码，且该代码与**当前已加载的股票代码不同**时，在**发起新公司请求的当下**（不是等待响应返回后）立即重置估值卡片。
- 覆盖所有换股入口：点击「查询」、输入框回车、选中搜索联想、点击欢迎页示例代码、从「估值记录」抽屉跳转等，只要最终经 `doSearch()` 且代码发生变化，均须重置。
- **同一代码重复查询不重置**：保留用户在当前股票上已调好的参数与结果，避免误清。
- 首次查询（当前尚未加载任何股票）按默认值初始化，不视为「残留清理」。
- AI「套用到估值」不涉及换股，**不触发**重置（它本来就要把推荐参数写入当前卡片）。
- 重置为静默操作，不弹提示。

#### FR-12.2 重置范围（全量）

1. **清空结果展示**：估值卡片不再显示上一家公司的任何内容，包括公司价值、股权价值、每股股权价值、基期自由现金流、金融资产价值、长期股权投资价值、经营资产价值、口径提示（`notes`）与参数摘要行。
2. **清空状态**：清空估值错误提示 `valError`；结束上一轮的 `valLoading` 状态（新请求会重新开启）。
3. **参数重置为页面默认值**（精确口径，与页面初始值一致）：

| 参数 | 重置值 |
| --- | --- |
| 估值模型 `model` | `perpetual`（永续增长模型） |
| 折现率 `r` | `8`（%） |
| 永续增长率 `g` | `3`（%） |
| 第一阶段增长率 `g1` | `10`（%） |
| 第一阶段年数 `n1` | `5`（年） |
| 第二阶段增长率 `g2` | `3`（%） |
| 第二阶段年数 `n2` | `5`（年） |
| 终值永续增长率 `g3` | `3`（%） |
| 基期 FCF 选取方式 `fcf_mode` | `latest`（最近一年） |
| 基期 FCF 选取年数 `fcf_years` | `3`（年） |
| 自定义基期 FCF 值 `fcf_custom_value` | 空 |
| 自定义基期 FCF 单位 `fcf_custom_unit` | `yi`（亿） |
| 研发调整 `adjust_rd` | 关闭 |

- **不保留任何上一家公司的参数**：当前系统没有任何持久化的估值参数「全局偏好」，刷新页面即回默认，因此切换股票时全量回默认，不做部分保留。
- 不属于「公司估值」卡片的状态**不受影响**：AI 分析模式（`aiReasoning`）、AI 分析结果（切换股票时按现有逻辑清空）、三大报表与六维分析的年份筛选、搜索历史等均不在重置范围内（按各自既有逻辑处理）。

#### FR-12.3 竞态防护（当前实现缺陷，必须修复）

- 现状：`doSearch()` 会自动发起估值请求，但 `fetchValuation()` 未校验响应是否仍属于当前股票。若上一家公司的请求晚于新公司请求返回，会**覆盖新公司的估值卡片**（与本次重置目标直接冲突）。
- 要求：
  - 每次估值请求携带**请求序号**（或等价的请求身份），并绑定发起请求时的 6 位代码。
  - 响应返回时，若当前代码已变化或请求序号不是最新，则**整体丢弃**该响应：不写 `valuation`、不写 `valError`、不改 `valLoading`、**不写估值记录**。
  - 新公司请求发起时的重置，配合上述守卫，保证卡片只可能展示当前公司的结果。
  - 手动「计算估值」与 AI「套用到估值」发起的请求同样受此守卫约束；被丢弃的旧请求不产生记录，也不弹错误。
- 竞态验收口径：快速依次搜索 A、B 两家公司（A 的估值响应人为延迟到 B 之后返回），最终页面必须只展示 B 的结果与参数，A 的结果不得出现，记录列表不得新增 A 的自动计算记录。

#### FR-12.4 与「估值记录」的关系

- 重置只作用于**当前页面的估值卡片显示与表单参数**，**不删除、不修改**服务端或 localStorage 中已保存的任何估值记录；抽屉中的历史快照不受影响。
- 重置本身不产生记录；新公司加载后自动执行的估值计算按 FR-1 同样不产生记录。
- 从估值记录跳转（FR-7）时：先按 FR-12 重置为默认，**再**回填该条记录的参数，最后由搜索流程自动计算。时序不可颠倒，否则会以默认参数计算或回填被重置覆盖。

### FR-13 后端读写 API（P0，本版新增）

所有接口沿用项目统一响应 `{code, data, message}`（`code=0` 成功）；路径固定为 `/api/valuation-history`。金额单位一律为**元**。成功响应的 `data` 统一为 `{ "items": [ValuationRecord...] }`，即**写入/删除后返回服务端完整的最新列表**（≤50 条），前端据此整体替换本地列表，避免前后端状态分叉。

#### FR-13.1 `GET /api/valuation-history` — 读取列表

- 请求：无参数。
- 响应（成功）：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [
      {
        "code": "600519", "name": "贵州茅台", "market": "sh",
        "createdAt": "2026-10-17T05:59:12Z", "source": "manual",
        "year": 2025, "model": "perpetual", "modelName": "永续增长模型",
        "discountRate": 8, "growthRate": 3,
        "stage1Growth": null, "stage1Years": null,
        "stage2Growth": null, "stage2Years": null, "terminalGrowth": null,
        "fcfMode": "latest", "fcfModeName": "最近一年", "fcfYears": null,
        "adjustRD": false, "rdAdjustment": null,
        "fcfCustomValue": null, "fcfCustomUnit": null,
        "baseFCF": 12345678900, "financialAssetValue": 50000000000,
        "longEquityValue": 1200000000, "operatingAssetValue": 200000000000,
        "companyValue": 251200000000, "debtValue": 0,
        "equityValue": 251200000000, "equityValuePerShare": 1999.36
      }
    ]
  }
}
```

- 服务端保证：按 `createdAt` 倒序、`code` 唯一、最多 50 条。
- 文件不存在/读取失败 → 返回 `code=0` + 空 `items`（不报错，见 FR-4.3）。

#### FR-13.2 `POST /api/valuation-history` — 新增或覆盖一条

- 请求体：**单个** `ValuationRecord`（字段见 FR-2）；`createdAt` 可省略，**即使传入也被忽略**，由服务端在写入时设置为当前时间（UTC ISO 8601）。`market`/`fcfModeName` 缺失时服务端可按 `code`/`fcfMode` 回填（与现有前端逻辑同口径）。
- 服务端处理（在锁内、单次原子写完成）：
  1. 校验 `code` 为 6 位数字，否则拒绝（HTTP 400，`code=1`）；
  2. 其余字段按 FR-4.3 归一化（非法类型置 `null`/丢弃）；
  3. 按 `code` 删除旧记录 → 新记录置顶 → 超过 50 条截断最早 → 按 `createdAt` 倒序；
  4. 原子写回文件；写失败则**不提交**任何变更并返回 `code=1`；
  5. 返回写入后的完整 `items`。
- 请求示例：

```json
{
  "code": "300750", "name": "宁德时代", "market": "sz", "source": "ai",
  "year": 2025, "model": "two_stage", "modelName": "两阶段模型",
  "discountRate": 9, "stage1Growth": 15, "stage1Years": 5, "stage2Growth": 3,
  "fcfMode": "average", "fcfModeName": "近几年平均值", "fcfYears": 3,
  "adjustRD": true, "rdAdjustment": 123000000,
  "baseFCF": 45600000000, "financialAssetValue": 80000000000,
  "longEquityValue": 0, "operatingAssetValue": 1400000000000,
  "companyValue": 1480000000000, "debtValue": 20000000000,
  "equityValue": 1460000000000, "equityValuePerShare": 331.08
}
```

- 调用时机严格遵循 FR-1：仅手动「计算估值」与 AI「套用」成功后调用；`auto` 自动计算不调用。

#### FR-13.3 `DELETE /api/valuation-history/:code` — 删除单条

- 路径参数：6 位代码；非法 → HTTP 400 + `code=1`。
- 删除存在/不存在的记录均为**幂等成功**（不存在即无操作），返回删除后的完整 `items`；写失败 → `code=1`。

#### FR-13.4 `DELETE /api/valuation-history` — 清空全部

- 清空后返回 `{"code":0,"message":"ok","data":{"items":[]}}`；写失败 → `code=1`，磁盘内容保持不变。

#### FR-13.5 错误约定

- 请求参数/请求体非法：HTTP 400，`{"code":1,"message":"<可读原因>","data":null}`。
- 存储读写失败（磁盘/权限）：HTTP 200，`{"code":1,"message":"保存失败：<原因>","data":null}`（沿用项目「业务错误走 200 + code=1」的惯例）。
- 错误信息应可读（如「保存失败：permission denied」），但不得包含密钥等敏感内容；前端只展示 `message`。

### FR-14 前端异步改造与失败处理（P0，本版新增）

- **数据源切换**：`valuationHistory` 内存列表的唯一起源改为服务端接口；`loadValuationHistory`/`saveValuationHistory`（localStorage）不再用于新增/删除/清空。
- **加载时机**：
  1. 应用初始化：`GET` 一次，用于顶栏徽标计数；失败则计数隐藏、不弹全局错误，不影响页面，用户打开抽屉时再重试；
  2. 每次打开抽屉：`GET` 一次（FR-5），并回到第 1 页。
- **写入时机**：
  - 估值成功且通过 FR-12.3 竞态守卫后（`source=manual`/`ai`）→ `POST` 一次；成功后用响应 `items` 替换本地列表并更新徽标；失败按 FR-10 提示，不加入列表。
  - 删除 → `DELETE /:code`；清空 → `DELETE` 全部（FR-8/FR-9）。
- **不保留 localStorage 兜底**（推荐结论）：服务端是唯一数据源，避免出现「本浏览器看得到、别的设备看不到」的分裂状态；网络/服务端失败时明确提示并保留上次成功加载的列表。
- **并发/乱序守卫**：前端为记录类请求维护单调序号（或等价的「最新响应才生效」标记）。多个 POST/DELETE 响应乱序返回时，只采用**最后一次发起**的请求响应更新列表，防止旧响应把新列表覆盖回去。
- **页面其他功能不受影响**：初始化 GET 失败、抽屉刷新失败、POST 失败均不得阻断估值计算、指标/报表/AI 等请求，也不得让整页不可用。
- **展示兼容**：前端仍对返回条目做基本防御（缺 `code`/时间非法则跳过），但不再负责去重、排序、50 条截断（由服务端保证）。

### FR-15 旧 localStorage 数据迁移（P1；若 Q6 确认迁移则按 P0 实现，本版新增）

- **推荐：迁移，不放弃旧数据。** 理由：迁移成本低（≤50 次 POST）、用户无感；放弃会让已有用户升级后记录归零，与「持久化升级」的预期不符。
- **触发与算法**（幂等，可中断重试）：
  1. 应用初始化 `GET` 服务端列表；
  2. 若 localStorage 中存在合法旧记录（信封 `{version:1, items}`，逐条按 FR-4.3 校验），对**服务端尚不存在的 `code`** 逐条 `POST`：按 `createdAt` **从旧到新**顺序发送，使服务端按写入顺序生成新时间戳，最终顺序与旧列表一致；
  3. 服务端已存在的 `code` **以服务端为准**，跳过（不覆盖他处较新的记录）；
  4. 全部成功后写入本地标记 `valuationHistoryMigrated=1`，并提示一次「已迁移 N 条本机估值记录到服务端」；标记存在时不再迁移。
  5. 部分失败：不写标记，提示「有 N 条估值记录迁移失败，将在下次打开时重试」；下次初始化只补发仍缺失的 `code`。
- **旧数据保留**：迁移成功后**不删除** localStorage 的 `valuationHistory`（作为一次升级备份，避免迁移逻辑缺陷导致数据不可恢复）；后续版本可再决定清理。
- **已知取舍**：迁移未完成期间，若用户在其他设备删除了某条已迁移记录，本浏览器下次补迁可能把它重新加回；该窗口仅在迁移未全部成功时存在，可接受。
- **搜索历史不迁移**：`stockSearchHistory` 仍为浏览器本地数据，不属于本次升级范围。

## 4. 非功能需求

- **性能**：记录类接口为本地文件读写，上限 50 条、文件 ≤50 KB；单次 `GET`/`POST`/`DELETE` 在本机环境应在 **100ms 内**完成（不含网络），不引入可感知延迟。估值接口本身耗时不变。
- **持久化**：服务端重启后记录仍在；进程异常退出不得损坏文件（原子 rename 保证旧文件完整）。
- **并发**：单进程内所有记录读写串行化，不出现丢失更新或半截文件；多进程/多实例场景见第 5 节。
- **体积**：单条约 0.6–1 KB，50 条约 30–50 KB；接口响应体最多约 50 KB。
- **兼容性**：后端仅用 Go 标准库（`encoding/json`、`os`、`sync`），**不新增第三方依赖**；前端仅使用现有 Vue 3 + Element Plus 与纯 JS，不改变构建方式（CDN）。
- **响应式**：桌面端抽屉 420px；≤768px 抽屉全宽；320px 视口下条目内容自动换行、无横向滚动，删除按钮触控目标不小于 32×32px。
- **易用性**：入口在欢迎页/结果页均可达；整条记录可点击且有 hover/焦点反馈；所有图标按钮带 `title` 与 `aria-label`；加载/失败态有明确文案与重试入口。
- **数据安全**：记录存放在服务端数据目录，不再上传至第三方；但**服务没有账号与鉴权**（默认监听 `0.0.0.0`），同一局域网内能访问服务的人即可读写/清空记录。记录仅含公开财报估值快照，不含密钥等敏感信息；如需隔离，用户应改为监听 `127.0.0.1` 或用防火墙限制（见第 5 节）。

## 5. 边界与约束

- **只记录估值**：不记录搜索行为、AI 分析结论、公司价值卡片、六维分析等其他数据。
- **新增后端接口仅限 FR-13 的 4 个**；不修改现有估值计算逻辑、接口参数与返回结构，不影响指标/报表/分析/AI 等既有接口。
- **不改动现有卡片布局与顺序**：估值记录放在顶栏抽屉中，结果区不新增常驻卡片。
- **切换股票即重置估值卡片**：新公司加载时清空上一家公司的估值结果与参数（FR-12）；这是当前卡片的状态重置，**不涉及**已保存的历史记录。
- **不做**：账号体系与鉴权、导出/导入、按公司内多版本对比、备注与标签、搜索/筛选/记录排序、估值提醒、估值参数的全局偏好持久化（切换股票一律回默认）、数据库/ORM、跨服务端实例的记录同步与冲突合并。
- **已知限制**：
  - 记录以**服务端数据目录**为准：同一服务端地址下换浏览器/设备可见；指向不同 `-data` 目录或不同服务器则各看各的。
  - 文件路径默认相对**进程工作目录**；从不同目录启动会生成不同的 `data/valuation_history.json`，需用 `-data` 固定。
  - **不支持多实例并发写**：两个进程指向同一文件时，互斥锁只在本进程内生效；原子 rename 能避免文件损坏，但会出现「后写覆盖先写」的丢失更新。推荐同一数据文件只由一个服务进程使用。
  - 记录文件可人工编辑，但格式错误时会被视为空列表（损坏文件另存备份，见 FR-4.3）；不支持在编辑后热加载——每次请求都会重新读文件，因此下次请求即生效。
  - 同一公司只保留最新一次估值，旧参数组合不可回看（若需要，见第 8 节 Q2）。
  - 记录不包含 `notes`，某些口径提示在记录中不可见；回到页面重算后仍会展示。
  - 点击记录后若历史数据已变化，重算结果可能与快照不同，属预期。
  - 搜索历史 `stockSearchHistory` 仍存 localStorage：不跨设备，也不参与本次迁移。
- **依赖**：`data.stock.name` 用于记录名称；`guessMarket` 用于市场徽标；`fmtYi`/`fmtNum` 用于格式化展示；服务端数据目录需可写。

## 6. UI 设计方案

### 6.1 放置位置候选与结论

| 候选 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 结果区新增「估值记录」常驻卡片（公司估值卡片之后） | 与估值功能相邻，算完即可见 | 记录是**跨公司全局数据**，放在单股结果区会让人误以为只含当前公司；页面已有 7 张卡片，移动端滚动进一步变长；欢迎页无法查看 | 不采用 |
| B. **顶栏入口 + 右侧抽屉** | 全局数据放全局位置；欢迎页/结果页随时可达；不占结果区版面；移动端全屏抽屉可读性好；与顶栏既有搜索历史入口风格一致 | 需一次点击才可见，发现性依赖入口曝光 | **推荐** |
| C. 顶栏下拉 Popover | 更轻量 | 记录多条时 Popover 易溢出、移动端操作不便、删除/清空确认体验差 | 不采用 |
| D. 左侧/右侧固定侧栏 | 常驻可见 | 需重排现有 1120px 单列布局，窄屏无空间，改动大收益低 | 不采用 |
| E. 结果区可折叠卡片 | 兼顾相邻性与收纳 | 仍是单股上下文，且折叠状态增加一次点击 | 不采用 |

**结论：顶栏常驻入口「估值记录」+ 右侧抽屉**。入口放搜索区右侧、品牌行内；桌面显示「图标 + 文字 + 数量」，移动端收为「图标 + 数量」，不挤占搜索框。

## 9. 待确认问题（本次后端持久化升级）

> 以下问题会显著影响使用方式，正文已按推荐值写成可落地的默认口径；用户确认后可直接进入技术设计，不确认则按推荐值执行。

- **Q5 记录文件放哪里？**
  - 影响：数据可见性、备份方式、从不同目录启动是否会「丢记录」。
  - 推荐：新增 `-data <目录>` 启动参数，缺省 `./data`，文件为 `<data>/valuation_history.json`（相对进程工作目录）；`.gitignore` 忽略 `/data/`。
  - 理由：项目是单二进制、无数据库的个人工具，工作目录下的 `data/` 最直观、易备份；不引入跨平台用户目录解析。
  - 备选：放系统用户数据目录（`os.UserConfigDir()`），不受工作目录影响，但路径不直观、跨平台不一致。

- **Q6 是否迁移浏览器里已有的旧估值记录？**
  - 影响：升级后用户是否「记录归零」；迁移逻辑的一次性复杂度。
  - 推荐：**迁移**。首次加载检测 localStorage 旧记录，把服务端缺失的 `code` 按旧时间从早到晚逐条 POST；全部成功后写标记，保留 localStorage 原数据作为备份（不删除）。服务端已有的同 `code` 以服务端为准；部分失败下次补迁。
  - 理由：成本低（≤50 次请求）、用户无感；放弃旧数据会与「持久化升级」的预期相悖。
  - 备选：不迁移、从零开始（实现最简单，但老用户记录丢失）。

- **Q7 记录接口是否接受「无鉴权」？**
  - 影响：同一局域网内能访问服务的人可读取、删除、清空估值记录；记录只含公开数据的估值快照，敏感度低。
  - 推荐：本期**不加鉴权**，与现有全部只读接口保持一致；文档告知可用 `-addr 127.0.0.1:18080` 仅本机访问。
  - 理由：项目定位为单用户个人工具，引入账号体系超出本次范围；新增鉴权会牵连所有接口与前端。
  - 备选：仅对写接口加简单口令/Token（需新增配置与前端输入，收益有限）。

**推荐方案一句话**：用 `-data`（默认 `./data`）下的单个 `valuation_history.json` 存全部记录，服务端以互斥锁 + 临时文件 rename 原子读写，暴露 4 个 `/api/valuation-history` 接口并统一返回完整列表；前端改为异步调用（无 localStorage 兜底），旧 localStorage 记录首启自动迁移并保留备份，搜索历史维持现状。
