# 股票搜索支持名称与模糊匹配

> 来源：用户反馈（2026-09-27）「对于搜索功能，我想不仅能够通过股票代码来查询，也可以通过股票名称来查询，甚至可以支持模糊搜索」。
> 对应现状代码：
> - 前端 `internal/web/app.js`：搜索框为 `el-autocomplete`（模板约 815–832 行，`placeholder="输入A股代码，如 600519"`），`querySearch()`（约 749–754 行）目前**只在本地搜索历史里过滤**（localStorage `stockSearchHistory`，最多 10 条，约 287–290 / 726–743 行），`doSearch()`（约 483–489 行）直接以 `code.value.trim()` 拼进 `/api/stock/${code}/...` 路径；空态示例代码 `pickCode()`（约 491–495 行）同样直接填入代码查询。
> - 后端 `internal/api/handler.go`：`GetIndicators`（38–43 行）等 handler 以 `len(code) != 6` 校验并报「股票代码需为6位数字」；路由 `internal/api/router.go` 15–19 行均为 `/api/stock/:code/...`。
> - 数据源 `internal/client/eastmoney.go`：行情走腾讯 `qt.gtimg.cn/q=<prefix><code>`，`quotePrefix()`（79–85 行）按首位数字推断交易所（6/9→`sh`，其余→`sz`）。
> - 产品说明见 `docs/产品设计文档.md`（8 行、43 行、92 行）：现有核心流程为「输入股票代码 → 拉取财报+行情 → 计算指标 → 展示」。
>
> **需求范围（已定稿）**：本期支持「6 位代码 + 股票名称」的**任意子串包含**匹配（精确命中 > 前缀命中 > 其他子串，同层按代码升序），并**支持首字母拼音搜索**（东财 `PinYin` 字段原生提供，零边际成本；**不支持全拼**）；检索数据源选型与北交所取数前缀修正**待技术设计确定**。决策依据见第 7 节「已决策记录」。

## 1. 背景与目标

### 1.1 背景

当前搜索是**纯代码搜索**，且联想能力仅限于「本机搜过的历史记录」：

- 用户必须事先知道 6 位股票代码才能查询；记得公司名却不记得代码时**无法查询**，体验上与「A股财报分析工具」的定位不匹配。
- `el-autocomplete` 的下拉联想**只覆盖历史记录**（`querySearch` 从 `history` 里 filter），从未搜过的股票没有任何提示；输入过程中只做 `String.includes` 的历史过滤，不是真正的股票检索。
- 输入非 6 位时，前端把输入原样拼进 URL，由后端返回「股票代码需为6位数字」（`GetIndicators` 40–42 行），用户拿到的是一个报错而不是「你是不是想找 XX」的候选。
- 项目内**没有任何「名称 → 代码」的映射数据**（代码里 grep 不到股票列表 / 联想 / 搜索接口），这是本需求新增能力的核心依赖，其数据来源属技术设计范畴（见 FR-7）。

### 1.2 目标

- 用户在搜索框输入**股票名称的任意子串**（如「茅台」「贵州」「宁德」），或**股票代码的任意子串**（如 `0519`、`600`），均能得到包含「代码 + 名称 + 市场」的候选列表，并选中其中一条完成查询。
- 唯一明确命中时（如输入完整 6 位代码、或输入唯一完整名称后回车），可直接进入查询，不强迫用户多点一次。
- 无命中时给出明确、可读的提示，而不是抛后端报错。
- 现有「输入 6 位代码 → 回车/点查询」的行为**完全不变**，历史记录联想能力**保留并增强**。

## 2. 用户故事 / 使用场景

- 作为只记得公司名、不记得代码的个人投资者，我想要输入「贵州茅台」甚至只输入「茅台」就能从候选里选中它，以便不用先去别处查代码。
- 作为知道大致代码、只记得前几位或后几位的用户，我想要输入 `6005` 或 `0519` 也能联想出目标股票，以便减少翻找和试错。
- 作为反复查看同几只股票的用户，我想要下拉里优先出现我最近搜过的股票，同时也能直接搜到从没搜过的新股票，以便用一套输入框满足「快速回访」和「查找新标的」两种需求。

## 3. 功能需求

> 术语：**候选** = 下拉联想列表中的一条（含代码、名称、市场标识）；**命中** = 输入内容与某股票的代码或名称（或首字母，见 FR-2）发生匹配。

### FR-1 输入框同时接受代码与名称（P0）

- **触发**：用户在顶部搜索框输入任意内容（键盘输入、粘贴均可）。
- **要求**：
  - 输入内容应同时按**股票代码**、**股票名称**、**拼音/首字母**三条路匹配（见 FR-3），用户无需切换模式、无需加前缀（不做 `code:` / `name:` 之类的语法）。
  - 代码匹配：忽略输入中的空格；输入为数字时按数字子串匹配 6 位代码。
  - 名称匹配：按中文名称子串匹配，**大小写不敏感**（名称含字母时，如 `TCL`、`ST`，大小写视为相同）。
- **边界**：
  - 输入前后空格应被忽略（`" 茅台 "` 等价于 `"茅台"`）。
  - 输入 1 个字符即触发联想（不设最小长度门槛），但联想请求需防抖（见 NFR-2）。
  - 输入空字符串时不发起检索请求，仅展示最近搜索历史（见 FR-6）。

### FR-2 模糊程度：任意子串包含，精确/前缀优先（P0，用户已决策）

- **触发**：同 FR-1。
- **要求**：匹配范围为**任意子串包含**（不是仅前缀，用户已拍板，见第 7 节 D1），即输入内容出现在代码或名称的任意位置均算命中：
  - 「茅台」应命中「贵州茅台」，输入「州茅」也应命中（子串）；
  - 代码输入 `0519` 应命中 `600519`。
- **排序**：命中结果固定按「精确命中 > 前缀命中 > 其他子串命中」排列，同层级按**代码升序**（用户已拍板，见第 7 节 D1；纯排序、无随机，保证多次相同输入结果一致）：
  1. 名称**恰好等于**输入、或代码**恰好等于**输入的候选（精确命中，排首位）；
  2. 名称或代码**以输入开头**的候选（前缀命中）；
  3. 其余子串命中；
  4. 同一条股票同时被代码和名称命中时**只出现一次**（去重，去重不改变其对外的排序位次）。
- **输出**：候选总数最多 10 条（与现有历史上限一致，便于复用列表样式），超出则截断并仍保持上述排序。
- **边界**：命中结果为空时不返回空列表给用户干等，按 FR-5 提示。

### FR-3 拼音 / 首字母搜索（P1，本期启用）

- **状态**：**本期实现**（用户已决策，见第 7 节 D2）。检索数据源（东财搜索接口）**原生提供** `PinYin` 字段，无需自行引入拼音库或额外数据字段，边际成本为零。
- **要求**：按数据源实际能力，支持**首字母缩写**命中，**不支持全拼**：
  - **首字母缩写**（支持）：如 `gzmt` → 命中「600519 贵州茅台」，`tclkj` → TCL科技，`btr` → 比亚迪；大小写不敏感。
  - **全拼**（**不支持**）：东财 `PinYin` 字段**只存首字母**，`maotai` / `guizhoumaotai` / `ningde` 等全拼输入返回 `TotalCount=0`、无命中。此为**数据源能力限制，不是缺陷**，本期不通过自建拼音库补齐。
- **排序**：首字母命中纳入 FR-2 统一排序，排在**中文名称子串命中之后**、同一「精确/前缀/子串」层级内按代码升序。
- **边界 / 异常**：
  - 数据源未返回 `PinYin` 字段（如部分股票该字段为空）时，该股票按无拼音参与匹配，不报错、不影响其中文名与代码匹配。
  - 字母输入（首字母或全拼，无论是否命中）不得报错、不得阻塞 FR-1/FR-2 的中文与代码匹配。
  - 纯字母输入同时可能匹配名称中的英文字母（如 `TCL`、`ST`）与首字母拼音，两类命中均保留并按 FR-2 排序。
  - **明确非目标**：不实现全拼匹配，不得因全拼无命中而误判为 Bug 或引入额外拼音数据。

### FR-4 联想下拉：候选展示与交互（P0）

- **触发**：输入内容变化后，联想返回候选。
- **要求**：
  - 复用现有 `el-autocomplete` 下拉，每条候选**必须**展示：**股票代码**、**股票名称**、**市场标识**（见 FR-8，用户已定稿）；当前价为**可选**展示（有则显示、无则不显示，不因取价拖慢联想，见第 7 节 D4）。
  - 鼠标点击候选、键盘上下键选中后回车，均应完成「填入代码并触发查询」（等价于现有 `handleSelect`）。
  - 下拉中候选数 > 0 时，输入框回车行为：若当前输入能被解析为唯一候选，则直接查询该股票（见 FR-5）；否则不自动查询，保持下拉打开提示用户选择。
  - 联想请求返回前用户继续输入时，**只展示最后一次输入对应的候选**（丢弃过期响应），不得出现“输入变了、候选还是旧的”。
- **边界**：网络失败 / 联想接口不可用时，联想区静默降级（不弹错、不阻塞），用户仍可直接输入 6 位代码查询。

### FR-5 命中策略：唯一命中直进、多命中选择、无命中提示（P0）

- **触发**：用户点击「查询」按钮、或在输入框回车。
- **要求**：
  - **精确唯一命中**：输入恰为 6 位数字代码，或恰为某股票完整名称且该匹配唯一时，直接进入该股票的查询流程（保持现有 `doSearch()` 行为，不新增一次点击）。
  - **多命中**：输入非上述精确情形但存在多个候选时，输入框回车**取排序第 1 条候选直接发起查询**（用户已拍板，见第 7 节 D3）；下拉仍展示全部候选，鼠标点击/键盘选中其它条目可改查对应股票。
  - **无命中**：输入内容检索不到任何候选时，**不发起** `/api/stock/:code/...` 请求（避免后端返回「代码需为6位数字」这类原始报错），而是在搜索框下方/联想区给出可读提示，文案推荐：「未找到匹配的股票，请检查名称或 6 位代码」，并提示可用的输入示例。
- **异常**：输入为空时点查询不产生任何请求，也不报错（保持现状）。

### FR-6 保留并整合搜索历史（P1）

- **触发**：输入框获得焦点、且当前输入为空；或输入内容同时匹配历史。
- **要求**：
  - 输入为空、聚焦时下拉展示**最近搜索历史**（沿用现有 localStorage 存储与「最多 10 条、重复则提到最前」规则）。
  - 输入非空时，下拉结果 = **检索候选 ∪ 命中的历史记录**，同一股票只出现一次，历史命中可作为排序的同级加权（推荐历史优先，便于快速回访）。
  - 现有的「清空搜索历史」按钮行为不变；历史记录的展示样式（代码 + 名称）保持，并补充市场标识以与 FR-4 一致。
- **边界**：无历史且输入为空时，下拉可不展开或展示空态提示，不得报错。

### FR-7 名称/代码检索数据来源（P0，方案待技术设计确定）

- **要求**：系统应提供一个「按关键字检索股票」的能力，返回候选的**代码、名称、市场**字段，供前端联想与「名称 → 代码」解析使用。
- **交互约定（需求层面，不含实现）**：
  - 该能力应对前端暴露为**独立接口**（推荐 `GET /api/stock/search?q=<关键字>`，返回统一 `{code, data, message}` 结构，`code==0` 为成功，`data` 为候选数组），与现有 `/api/stock/:code/...` 调用方式一致。
  - 无论用户输入的是名称还是代码，**最终请求财报/行情接口时必须使用解析出的 6 位代码**（现有 API 只认 `:code`）。
- **数据源选型、是否本地缓存、是否离线股票列表**：**待技术设计确定**，本需求不限定实现方案（候选方向：东财搜索联想接口、或维护一份本地 A 股代码-名称清单；两者取舍由 `techexpert` 定）。
- **非目标**：不要求支持海外/港股/美股/B 股，不要求搜索财务科目或报表内容。

### FR-8 市场标识与歧义处理（P0）

- **触发**：候选展示（FR-4）、历史展示（FR-6）。
- **要求**：
  - 每条候选必须标识所属市场：**上证（sh）/ 深证（sz）/ 北交所（bj）**，推荐以简短徽标或后缀展示（如 `600519 贵州茅台 · 沪`）。
  - 当多个候选名称相同或高度相似时，**必须**同时给出代码与市场以区分（例如同名不同代码、或 `ST`/`*ST` 前缀差异），不得只靠名称让用户猜。
  - 名称中的 `ST` / `*ST` / 退市标识应**原样保留展示**，不隐藏、不截断（除非达到 FR-4 的候选宽度上限，可截断并保留完整名称于提示中）。
- **边界（已知现状限制）**：现有 `quotePrefix()` 仅区分 `sh`/`sz`，北交所（`8`/`4` 开头等）代码会被误判为 `sz`；若本次检索数据源能给出准确市场，候选的市场标识应以检索结果为准，行情取数前缀问题是否一并修正**待技术设计评估**（属实现层，见第 7 节 D5）。

### FR-9 移动端适配（P1）

- **触发**：视口宽度 ≤768px（沿用 `style.css` 现有断点）下使用搜索。
- **要求**：联想下拉宽度不超过视口、不产生横向滚动；候选行内代码、名称、市场标识在窄屏下不重叠、不截断成不可读；候选可正常点按（触控目标高度足够）。
- **边界**：320px 极窄屏下，长名称允许省略号截断，但代码与市场标识必须完整可读。

## 4. 非功能需求

- **确定性**：相同输入关键字对应**相同候选集合与相同顺序**（无随机、无时间依赖），便于用户形成预期、便于测试断言。
- **性能 / 防抖**：联想请求须防抖（推荐 200–300ms），避免逐字符高频请求；单次联想响应应在 1s 内返回，超时则按 FR-4 边界静默降级。
- **兼容性**：无构建步骤的内嵌前端（`internal/web/`，Vue 3 + Element Plus CDN）直接改造，不引入新的前端框架/构建工具；桌面端与移动端主流浏览器正常。
- **易用性**：输入过程中的任何状态（加载中、无候选、失败）都不得导致输入框卡死或值被清空；用户已输入的内容不得被联想流程覆盖。
- **无回归**：输入 6 位代码查询的既有链路（指标、三大报表、R3 分析、R4 估值）与展示不变；搜索历史、示例代码点击（`pickCode`）行为保持。
- **外部依赖约束**：若数据源为外部接口（东财等），须容忍其不可用/限流，降级后不影响「6 位代码直接查询」这一基础能力。

## 5. 边界与约束

- **非目标**：
  - 不做多条件筛选（行业/市值/PE 区间）、不做批量对比（延续《产品设计文档》5.4「明确不做」）；
  - 不改变任何指标的取值口径、估值公式与 AI 分析逻辑；
  - 不改变后端 `/api/stock/:code/...` 的既有路由语义（`:code` 仍为 6 位代码）；
  - 不做全文检索财报科目/正文。
- **依赖**：
  - 新增「关键字 → 候选（代码/名称/市场）」的检索数据源或接口（FR-7，方案由技术设计定）；
  - 复用现有 `el-autocomplete`、搜索历史 localStorage、`doSearch()` 查询链路。
- **已知限制**：
  - 拼音搜索依赖东财 `PinYin` 字段（FR-3）：**仅支持首字母缩写**（`gzmt` → 600519 贵州茅台）；**全拼不支持**（`maotai` → 无命中），此为数据源限制、非缺陷，本期不补齐；
  - 现有行情前缀推断不支持北交所，市场标识与取数的准确性受数据源与实现影响（FR-8 边界，见第 7 节 D5）；
  - 名称匹配基于数据源提供的名称口径，若数据源使用简称而用户输入全称（或反之）可能匹配不到，届时以「无命中提示」兜底。

## 6. 验收标准

- [ ] 输入 `茅台` 出现候选「600519 贵州茅台」；输入 `州茅`（子串）同样出现该候选。
- [ ] 输入 `0519` 出现候选「600519 贵州茅台」（代码子串命中）。
- [ ] 输入 `600519` 回车，直接进入该股票查询，行为与改动前一致。
- [ ] 输入某股票**唯一完整名称**后回车，直接查询对应股票；无需再从下拉点选。
- [ ] 输入同时命中多只股票的关键字时，下拉展示多个候选；此时**回车直接查询排序第 1 条**，点击/键盘选中其它候选则改查对应股票。
- [ ] 候选按「精确命中 > 前缀命中 > 其他子串命中」排序，同层级顺序稳定（多次相同输入结果一致）。
- [ ] 每条候选同时显示代码、名称、市场标识；同名/相似名称的候选可凭代码与市场区分。
- [ ] 输入查不到任何股票时，给出可读的中文无命中提示，且**不出现**后端「股票代码需为6位数字」的原始报错。
- [ ] 焦点在空输入框时，下拉展示最近搜索历史（最多 10 条）；非空输入时历史命中与检索候选合并去重。
- [ ] 联想请求去抖（连续快速输入不逐字符发请求）；快速连续输入后下拉只展示最后一次输入的候选。
